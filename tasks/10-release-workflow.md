# Task 10 — `.github/workflows/release.yml`: build and publish on tag `v*`

PR: https://github.com/hexember/active-browser/pull/12

## Goal
Add `.github/workflows/release.yml` — the last file in `Project.md` §4 — so that pushing a `v*` tag builds ActiveBrowser on a `macos-latest` runner with `make release` and publishes `ActiveBrowser.app.zip` + `SHA256SUMS` as GitHub Release assets under exactly the names `install.sh` downloads. One new file; no Swift, no `Makefile`, no `install.sh`, no `Project.md`.

## Spec (planner)

### Decisions to read before writing anything

**W1 — Scope fence: exactly one new file.**
`.github/workflows/release.yml` (`Project.md` §4, verbatim path — `.yml`, not `.yaml`, not `release-v1.yml`). Nothing else: no `Sources/`, no `Support/`, no `Package.swift`, no `Makefile`, no `install.sh`, no `Project.md`, no `README`, no `.gitignore`, no second workflow, no `.github/dependabot.yml`, no `CODEOWNERS`, no issue templates. Task 09 shipped `make release` and `install.sh` and this task **consumes** them unchanged — if something about them looks wrong, that is a `[RE-PLAN REQUEST]`, not an edit. The workflow must also never run `make install`, `make run`, `make clean`, `lsregister`, `open`, `defaults`, `xcode-select -s`, or anything touching Launch Services: a CI runner has no Launch Services story and those commands only exist here to manipulate a developer's machine.

**W2 — Trigger: `push` on `tags: ['v*']`, and nothing else.**

```yaml
on:
  push:
    tags:
      - 'v*'
```

No `pull_request`, no `workflow_dispatch`, no `schedule`, no branch filter. The reasoning is not stylistic:
- The job's only action is `gh release create "$GITHUB_REF_NAME"`. On any non-tag trigger `github.ref_name` is a **branch** name, so a `workflow_dispatch` run would either fail or publish a release named `main`. Adding `workflow_dispatch` therefore requires a `if: startsWith(github.ref, 'refs/tags/')` guard as well, which is two more moving parts for a button nobody needs in v1. If a future task wants a dry-run button, it adds **both** at once.
- A `pull_request` trigger would run `make release` on every PR to produce an artefact nothing consumes, on 10×-billed macOS minutes.

State in a header comment that **the workflow file must already exist on the commit the tag points at.** GitHub reads the workflow from the tagged commit's tree; a tag pushed onto a commit that predates this PR's merge triggers nothing at all. That is precisely why every GitHub-facing Test Step in this task is a `user` step gated on the stack being merged.

**W3 — `permissions: contents: write`, at the top level, and nothing else.**
`gh release create` with the automatic `GITHUB_TOKEN` needs `contents: write`. Declaring the block explicitly matters twice over: repository/org settings can default the token to read-only (in which case the run fails with an opaque `HTTP 403`), and declaring **any** `permissions:` block sets every scope not listed to `none`, which is the least-privilege posture for a workflow that also runs arbitrary build code. Do not add `packages:`, `id-token:`, `pull-requests:` or `actions:` — none is used.

**W4 — Runner, timeout, shell.**
- `runs-on: macos-latest`. `Project.md` §3 Phase 6, verbatim. Consequence recorded in W8: today's `macos-latest` image is Apple silicon, so the artefact is **arm64-only**.
- `timeout-minutes: 20` on the job. The default is **360** — six hours of a macOS runner, billed at 10× — for a job that should finish in two to four minutes. A hung `swift build` or a `gh` call waiting on a prompt must not be able to burn that.
- `defaults: { run: { shell: bash } }`. GitHub's implicit default for `run:` on macOS is `bash -e`; writing `shell: bash` explicitly selects `bash --noprofile --norc -eo pipefail`, i.e. it **adds `pipefail`**. Every `run:` block in this file contains a pipeline or a subshell whose failure must not be swallowed (W7's `shasum -c`), so this is load-bearing, not decoration.
- `name: release` at the top of the file and `jobs.release:` as the job id — `Project.md` Phase 6 Verify 2 says "the `release` workflow runs green", and that is the name the user will look for in the Actions tab.

**W5 — Steps, in order.** Five, no more:

1. **`actions/checkout@v4`** with default options. No `fetch-depth: 0` (`make release` reads no git history; a full clone is slower for nothing), no `submodules`, no `token:` override.
2. **Toolchain diagnostics** — one `run:` block printing `sw_vers -productVersion`, `uname -m`, `xcode-select -p`, `swift --version`, `gh --version`. This costs one second and converts the single most likely CI failure (an image whose default Xcode predates Swift 6, against `// swift-tools-version:6.0`) from a mystifying SwiftPM manifest error into a line at the top of the log. **Do not** "fix" the toolchain pre-emptively with `sudo xcode-select -s /Applications/Xcode_16.app` — the image-specific path rots, and pinning a version nobody has observed failing is a guess. If the diagnostics ever show Swift < 6.0, that is a `[RE-PLAN REQUEST]` with the log in hand.
3. **`make release`** — one line, no flags, no `-j`. This is the whole point of the task: CI runs the *same* recipe a maintainer runs locally, so there is exactly one way to cut a release.
4. **Verify the artefacts (W7)** — before anything is published.
5. **Publish (W6)** — `gh release create`.

**W6 — The publish step: the asset names are a public API, and `install.sh` is the client.**

`install.sh:149-153` downloads exactly these two URLs:

```
https://github.com/hexember/active-browser/releases/download/<tag>/ActiveBrowser.app.zip
https://github.com/hexember/active-browser/releases/download/<tag>/SHA256SUMS
```

(plus the no-API fallback `…/releases/latest/download/<same two basenames>`, `install.sh:146`). `gh release create` names each asset after the **basename** of the path it is given, so the upload arguments must be literally `build/ActiveBrowser.app.zip` and `build/SHA256SUMS`. Three things are therefore forbidden, and each silently breaks the one-liner for every future user while the workflow still goes green:

- **The `path#label` form.** `gh release create … 'build/ActiveBrowser.app.zip#ActiveBrowser (Apple silicon)'` renames the asset. A `#` anywhere in an upload argument is a bug.
- **Versioned asset names** — `ActiveBrowser-v0.1.0.app.zip`, `ActiveBrowser-arm64.zip`, `SHA256SUMS.txt`. `install.sh` builds a deterministic URL from the tag and the fixed basename; anything else 404s.
- **Renaming or moving the files before upload.** Upload them from `build/` where `make release` wrote them.

Shape of the step:

```yaml
      - name: Publish the release
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          gh release create "$GITHUB_REF_NAME" \
            --verify-tag \
            --title "$GITHUB_REF_NAME" \
            --notes-file "$RUNNER_TEMP/notes.md" \
            build/ActiveBrowser.app.zip \
            build/SHA256SUMS
```

Notes on each part:
- `GH_TOKEN` is set **on this step only**, not job-wide, so the build steps never see a credential.
- `$GITHUB_REF_NAME` is the tag (`v0.1.0`) because W2 guarantees a tag trigger. Prefer the environment variable over `${{ github.ref_name }}` interpolated into the script body — expression interpolation into a shell string is the standard script-injection shape, and while a tag name is not attacker-controlled in a solo repo, the env form costs nothing and is the habit to keep.
- `--verify-tag` makes `gh` refuse to *create* a tag that does not already exist on the remote, turning any future misconfiguration into a failure instead of a phantom tag.
- **No `--clobber`, no `gh release upload` fallback, no `--draft`.** If a release for the tag already exists (a re-run after a partial failure), `gh release create` fails loudly — the right default: published bytes are never silently overwritten. Record the recovery in the header comment: `gh release delete <tag> --yes` then re-run the workflow, or `gh release upload <tag> --clobber` by hand.
- **No `--prerelease` logic.** A tag like `v0.2.0-beta1` matches `v*` and would be published as a full release, becoming "latest" for `install.sh`. That is a documented v1 limitation for the header comment, not code.

**W7 — The verify step: enforce task 09 D6's hand-off in CI.**
`install.sh` cannot verify a `SHA256SUMS` that has more than one line or a path-prefixed filename (macOS ships Perl's `shasum`, which has no `--ignore-missing`; task 09 D6 and its *Architectural notes* both flag this at this task by name). Nothing else in the pipeline would catch a regression there — the release would publish green and only fail on a stranger's machine. So, before publishing:

```bash
test -f build/ActiveBrowser.app.zip
test -f build/SHA256SUMS
[ "$(wc -l < build/SHA256SUMS)" -eq 1 ]
grep -qE '^[0-9a-f]{64}  ActiveBrowser\.app\.zip$' build/SHA256SUMS
( cd build && shasum -a 256 -c SHA256SUMS )
```

The `grep` asserts both halves of D6 at once: exactly one entry, and a **bare** filename (a `build/` prefix or a renamed zip fails the anchor). The `cd build` subshell is `Project.md` Phase 6 Verify 1 verbatim and is why W4 mandates `pipefail`-bearing `shell: bash`. Optionally also `test ! -e build/ActiveBrowser.app` as a canary that task 09 D2's `rm -rf $(BUNDLE)` line is still in the recipe; harmless on an ephemeral runner, meaningful as a signal.

**W8 — Architecture: the runner builds arm64-only, and the Release must say so.**
Task 09's *Architectural notes* handed this task the universal-binary question. Decision for v1: **stay single-arch and be explicit about it.**

| Option | Verdict |
|---|---|
| (a) Build universal (`swift build -c release --arch arm64 --arch x86_64`, or two builds + `lipo -create`) | **Rejected here.** It requires editing `Makefile`'s `build:`/`bundle:` (`BUILD` moves to `.build/apple/Products/Release/$(APP)`), which W1 forbids and task 09 froze. It is a real improvement and gets its own follow-up task. |
| (b) Publish arm64 and state it on the Release page | **CHOSEN.** `install.sh`'s `lipo -archs` guard (task 09 D7) already turns an Intel install into an honest refusal — `this release is built for arm64, this Mac is x86_64` — instead of an app that installs, holds the `http` handler and never launches. The remaining gap is that the user learns it *after* downloading; the release notes close it. |

So the notes body must state the architecture, and must **derive** it rather than hardcode it (`macos-latest` migrated Intel → Apple silicon once already and can move again):

```bash
arch="$(lipo -archs .build/release/ActiveBrowser 2>/dev/null || echo unknown)"
```

`.build/release/ActiveBrowser` survives `make release` (only `build/ActiveBrowser.app` is deleted, task 09 D2), so this works in the verify step or the publish step.

**W9 — The notes body, and the heredoc footgun.**
`--notes-file "$RUNNER_TEMP/notes.md"` (written under `$RUNNER_TEMP`, never into the checkout, so the tree stays clean). Required content, four items:
1. The supported one-liner, `curl -fsSL https://raw.githubusercontent.com/hexember/active-browser/main/install.sh | sh` — identical to `install.sh:12` and `Project.md` §3.
2. Requirements: macOS 13 or later, and the derived architecture from W8, saying plainly that other architectures are refused by the installer.
3. The contents of `build/SHA256SUMS`, so the checksum is readable without downloading.
4. One line that the bundle is **ad-hoc signed** and that `curl` does not set `com.apple.quarantine` (`Project.md` §3 signing note) — this is the sentence that pre-empts "is this safe" and it is true only for this install path.

**Write the static prose with a quoted heredoc (`<<'EOF'`) and the two interpolated values with separate `printf`/`cat` appends.** An *unquoted* heredoc executes backticks, and every markdown code span in those notes is backticked — `` `curl -fsSL …` `` inside `<<EOF` is a command substitution, not text. This is the kind of thing that fails only on the real release.

**W10 — Action pinning.**
Pin `actions/checkout@v4` — a **major tag**, not a SHA, and not `@main`. Rationale to record in a comment: the only action used is first-party (GitHub's own), the job's token is scoped to `contents: write` on this repo alone, and a major tag keeps picking up runner/Node compatibility fixes that a frozen SHA would not. SHA pinning is the stricter supply-chain posture and becomes worth its own `chore/` task the moment a **third-party** action enters this file — at which point that action is pinned by SHA and `checkout` follows suit. `@main` or an unpinned `actions/checkout` is never acceptable.

**W11 — No secrets, no keychain, no notarization.**
`make bundle` runs `codesign --force --sign -`, an ad-hoc signature, which needs **no identity and no keychain** and therefore works on a bare runner — no `security create-keychain`, no `APPLE_CERTIFICATE` secret, no `notarytool`, no `--sign "Developer ID Application: …"`. `Project.md` §3 defers Developer ID and notarization until a *quarantining* distribution path (browser download, Homebrew Cask) exists, and says `make sign` / `make notarize` land first. The only credential this workflow may reference is the automatic `secrets.GITHUB_TOKEN`; `secrets.` must appear exactly once in the file.

### Architectural notes and risks

- **The one irreversible coupling in this task is a pair of filenames.** `install.sh` constructs its download URLs from a tag plus two fixed basenames; `gh release create` derives asset names from the basenames of its arguments. Nothing at runtime reconciles the two. A rename on either side produces a green workflow, a healthy-looking Release page, and a one-liner that fails for every user with a bare 404. That is why the check is static, mutual, and stated as its own acceptance criterion — and why any future change to either file must be made in the same PR as the other.
- **This machine and the runner are different computers, and no assertion may cross between them.** Locally: CommandLineTools only, hence the `ld: warning: search path '/Library/Developer/CommandLineTools/…' not found` lines that every task in this run has had to filter. The runner has a full Xcode and **will not emit them**, so a CI warning gate written as "expect 2 warnings" would be wrong on day one — the workflow asserts nothing about warnings at all (the green-build guardrail is enforced pre-commit, locally). Conversely the runner's Swift version is unknown until the first real run, which is what W5's diagnostics step exists to surface.
- **`macos-latest` is a moving target in the one dimension that matters.** It is Apple silicon today; it was Intel in 2023. W8's derived `lipo -archs` means the Release page tells the truth either way instead of asserting a hardcoded `arm64` that quietly becomes a lie. The real fix — a universal binary — is a `Makefile` change and so a separate task; `install.sh`'s `lipo` guard is the safety net until then.
- **Version strings will not match the tag.** `Support/Info.plist` hardcodes `CFBundleShortVersionString 1.0.0`, so a `v0.1.0` release installs an app that reports `1.0.0`, and `install.sh` prints `ActiveBrowser 1.0.0 is installed`. Deliberately **not** fixed here: injecting `plutil -replace CFBundleShortVersionString -string "${GITHUB_REF_NAME#v}" Support/Info.plist` before `make release` would work (the plist is copied and *then* signed inside `make bundle`, so the signature stays valid), but it makes the CI artefact differ from a local `make release` and it is unspecified in `Project.md`. Follow-up task, with that one-liner as the starting point.
- **A re-run after a partial failure is a manual operation, on purpose.** Without `--clobber`, the second `gh release create` for the same tag fails. The alternative — silently replacing published bytes whose checksum users may already have recorded — is worse for a distribution channel than a red run and a documented `gh release delete`.
- **The GitHub API path in `install.sh` is still untested by machine anywhere in this run** (task 09's *Architectural notes* flagged it, and this task cannot fix that while the repo is private). It gets its first real execution at `user` Step 14. Its blast radius is bounded by design: one `grep` for `tag_name`, a deterministic asset URL, and a no-API redirect fallback. If Step 14 fails there, the failure mode is a clean `download failed: …` message, not a broken install — validation still precedes anything destructive (task 09 D7).
- **Private-repo reality, stated once so no one re-derives it.** `raw.githubusercontent.com`, `api.github.com/repos/…/releases/latest` and `github.com/…/releases/latest/download/…` all require public access or a credential. `install.sh` sends none. So on a private repo the *entire* default path of the installer — the product's headline feature — cannot be exercised, by anyone, including the user. Making the repo public is a deliberate one-time decision for the user (the repo carries no secrets; this workflow adds none), and it is listed as the precondition on every row that needs it rather than assumed.
- **Nine unmerged PRs sit below this one.** A tag pushed before they merge points at a commit whose tree contains no `.github/workflows/release.yml`, so GitHub would run nothing and the user would see an empty Actions tab and conclude the workflow is broken. Spelling this out in the header comment and in Step 12's precondition is cheap insurance against exactly that confusion.
- **This file is the last one in `Project.md` §4.** After it, the directory structure in §4 is complete and every Phase 1–6 deliverable exists. What remains is merge and cleanup, enumerated in *Next*.
