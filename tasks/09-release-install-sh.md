# Task 09 — `make release` (ditto zip + SHA256SUMS) and `install.sh`

Status: pr-open
Phase: 6
Branch: feature/release-install-sh
Base: feature/browsers-fallback-menu
PR: https://github.com/tajpuriya27/active-browser/pull/11

## Goal
Add the `release:` target to the existing `Makefile` (`ditto` zip + `SHA256SUMS`, **plus deletion of the `build/ActiveBrowser.app` it just zipped**, so `make release` inherits task 04's single-Launch-Services-record invariant instead of re-creating the duplicate that task cost a whole PR to eliminate) and a new repo-root `install.sh` that installs ActiveBrowser into `/Applications` from a checksum-verified zip, launches it, and registers its URL schemes. `install.sh` takes a documented **local-zip override** so the entire install path is testable on this machine before any GitHub Release exists. No Swift, no workflow file (that is task 10).

## Spec (planner)

### Decisions to read before writing anything

**D1 — Scope fence: exactly two files.**
`Makefile` (one word on `.PHONY`, one new target, one comment block) and a **new** `install.sh` at the repo root (`Project.md` §4). Nothing else: no `Sources/`, no `Support/Info.plist`, no `Package.swift`, no `Project.md`, no `README`, no `.gitignore`, and — the task-10 boundary — **no `.github/` of any kind**. `install.sh` must not appear in `Makefile` and `Makefile` must not gain an `uninstall:`, a `sign:` or a `notarize:` target (`Project.md` §3 Phase 6 defers the latter two until a quarantining distribution path exists). The `build`, `bundle`, `install`, `run` and `clean` recipes stay byte-identical to what task 04 shipped.

**D2 — THE decision in this task: `make release` deletes `build/ActiveBrowser.app` after zipping it.**

`release:` depends on `bundle:`, which unconditionally `rm -rf`s and re-creates `build/ActiveBrowser.app`. That is precisely the hazard task 04 measured and killed (`tasks/04-make-install.md` D2a): a second `.app` on disk declaring `com.local.activebrowser` and claiming `http`/`https` is registered by the Launch Services scanner **~1–3 s after the `make` target has already returned**, the record then persists indefinitely, and it puts a second, identical-looking *ActiveBrowser* row in System Settings → Desktop & Dock → *Default web browser* pointing at a path the next `make clean` deletes. Task 04's own closing note makes resolving this a stated obligation of this task.

| Option | Verdict |
|---|---|
| **(a) Leave `build/ActiveBrowser.app` in place and document it** | **Rejected.** It re-introduces the exact defect task 04 removed, and it does so in the target a *release* is cut with — i.e. the one most likely to be run right before the maintainer hands the app to someone. "Documented" does not help: the two dropdown rows are indistinguishable. |
| **(b) `lsregister -u build/ActiveBrowser.app` only** | **Rejected — measured not to work** (task 04 D2a, measurements 1 and 2, twice, in two different recipe positions). The whole target runs in under 2 s; the scan lands after it. You cannot race the scanner from inside a `make` recipe, and a `sleep` to buy the time is banned (task 04 D2a). |
| **(c) `rm -rf $(BUNDLE)` then `-$(LSREG) -u $(BUNDLE)`, as the last two recipe lines** | **CHOSEN.** Identical mechanism, order and rationale as `install:`: the `rm` removes the *cause* (the scanner registers what is on disk — with nothing there, no later scan can create a record), the `-u` afterwards sweeps any record an earlier scan already created. Both lines run **after** the zip and the checksum, so no artefact is lost. |

Exact recipe — five lines, real tabs:

```make
release: bundle
	rm -f build/$(APP).app.zip build/SHA256SUMS
	ditto -c -k --keepParent $(BUNDLE) build/$(APP).app.zip
	cd build && shasum -a 256 $(APP).app.zip > SHA256SUMS
	rm -rf $(BUNDLE)
	-$(LSREG) -u $(BUNDLE)
```

Line notes: the leading `rm -f` makes the target idempotent and removes any doubt about whether `ditto -c -k` truncates or appends to an existing archive (it is run twice in the Test Steps). `ditto -c -k --keepParent` is Apple's own archive form for a signed `.app` and is what puts `ActiveBrowser.app/` at the top level of the zip — `install.sh` depends on that name. `cd build && shasum …` is `Project.md` §5 verbatim and deliberately writes a **bare** filename, which is why D6 normalises the working directory before verifying. `rm -rf $(BUNDLE)` carries **no** leading `-` (a bundle that cannot be deleted breaks the single-record invariant and must be loud); `-$(LSREG) -u $(BUNDLE)` carries one (there is usually no record to remove and `lsregister -u` exits non-zero then — `make: [release] Error 1 (ignored)` is correct output). Add `release` to `.PHONY`; the existing comment above that line already mandates it.

Two consequences to state in the Makefile comment: **`make release` leaves `build/` holding only `ActiveBrowser.app.zip` and `SHA256SUMS`** (run `make bundle` if you want the `.app` back — it costs ~0.3 s and re-creates the duplicate record by design), and **task 10's workflow is unaffected**, since it consumes those two files and never the bundle.

**D3 — `install.sh`: interpreter, exec bit, and the two constraints `curl … | sh` imposes.**
- Shebang `#!/bin/bash`, file mode **`100755`** in git. The piped usage (`curl -fsSL … | sh`) ignores both, but the script is also run directly by this task's `ai` steps and by anyone who downloads it first; an exec bit is free, and mode drift is a silent papercut later. Verify with `git ls-files -s install.sh` → `100755`.
- `set -euo pipefail` on the first line after the header, non-negotiable (`Project.md` §3 step 1). macOS's `/bin/sh` **is** bash 3.2, so `pipefail` is available on the piped path too; write bash-3.2-compatible shell (no `mapfile`, no `${var,,}`, no associative arrays) and quote **every** expansion, so the script behaves identically if someone pipes it to `zsh`.
- **`set -u` + optional env vars:** every optional variable is read as `"${VAR:-}"`. A bare `$ACTIVEBROWSER_ZIP` under `set -u` aborts the script with an unhelpful message for every normal user.
- **`set -e` + `pipefail` + `grep`:** a `grep` that finds nothing exits `1` and kills the script with **no output**. Every `grep`/`sed` used to parse anything must be written `… || true` followed by an explicit empty-check that calls `fail` with a real message.
- **The script must never read stdin.** On the piped path stdin *is* the script's own remaining text, so any `read -p "continue? "` would eat the rest of the program. No prompts, no confirmations, no `read`.
- **The script must never use `$0` or `dirname "$0"`.** When piped, `$0` is `sh`/`-`, not a path. The local override (D5) is therefore an absolute/relative path supplied in an env var, never something derived from the script's own location.
- One `fail()` (message to **stderr**, `exit 1`) and one `say()`/`step()` progress printer; LF line endings, no CRLF, no BOM (`curl | sh` chokes on CRLF).
- Cleanup: `TMPDIR_WORK="$(mktemp -d)"` plus `trap 'rm -rf "$TMPDIR_WORK"' EXIT`. Every download, staging and verification happens inside it.

**D4 — Preflight refusals, and how they are made testable (`Project.md` §3 step 1).**
All of these run **before** anything is downloaded and long before anything is deleted; each calls `fail` with a message naming the value it saw:
1. `[ "$(uname -s)" = Darwin ]` — "ActiveBrowser is macOS-only (found: …)".
2. macOS version: `ver="$(sw_vers -productVersion)"`, major = `${ver%%.*}`, refuse if `< 13`. An integer compare on the major is sufficient and correct for every macOS that exists (10.x → `10`, then 11…15, 26); do not attempt a lexical or three-component compare.
3. Architecture: `arch="$(uname -m)"`, accept only `arm64` or `x86_64`. **Rosetta correction, required:** if `arch` is `x86_64` and `sysctl -n sysctl.proc_translated 2>/dev/null` prints `1`, the real machine is arm64 — set `arch=arm64`. Without this, an Apple-silicon user whose Terminal happens to be running under Rosetta is refused an artefact that would have worked.
4. `[ -w /Applications ]` — "/Applications is not writable by $(id -un); install as an admin user". **Never `sudo`, never suggest `sudo`** — a root-owned bundle in `/Applications` is one no later run of this script or of `make install` can replace.
5. Required tools present (`curl`, `ditto`, `shasum`, `unzip`-free by design). The Launch Services helper is the absolute path `/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister`; if it is **missing**, print a warning and continue — `open` still makes the app usable and a missing `lsregister` is not worth failing an install over. Everything else missing is a `fail`.

**Call the preflight tools by bare name (`sw_vers`, `uname`, `sysctl`), not by absolute path.** That is ordinary shell practice and it is what lets Test Step 6a exercise the macOS-13 refusal for real by putting a stub `sw_vers` on `PATH`, instead of the guard being "verified by reading it". `lsregister` is the single exception (it is not on `PATH`).

**D5 — Acquisition: the GitHub Release is the default; the local override exists for testing and is documented as such.**
Three environment variables, all documented in the header comment block, all read as `"${VAR:-}"`:

| Variable | Meaning |
|---|---|
| `ACTIVEBROWSER_ZIP` | Path to a local `ActiveBrowser.app.zip`. When set, **no network access happens at all** — no API call, no `curl`. This is the testing/offline path. |
| `ACTIVEBROWSER_SUMS` | Optional path to the `SHA256SUMS` for that zip. Default: `SHA256SUMS` **in the same directory as the zip**, which is exactly the shape `make release` produces in `build/`. |
| `ACTIVEBROWSER_VERSION` | Pin a release tag (e.g. `v0.1.0`) instead of resolving the latest. |

Remote path (the default, `Project.md` §3 step 2): resolve the tag from `https://api.github.com/repos/tajpuriya27/active-browser/releases/latest`, parsing **only** `"tag_name"` — one small, robust grep — then download the two assets from the deterministic URLs `https://github.com/tajpuriya27/active-browser/releases/download/$TAG/ActiveBrowser.app.zip` and `…/SHA256SUMS`. Do **not** parse `browser_download_url` out of the JSON: hunting asset URLs without `jq` (which is not installed on a stock Mac) is the fragile part of every script that does this, and the download URL is fully determined by the tag. If the API call fails or yields no tag (its unauthenticated limit is 60 requests/hour per IP), print a note and fall back to `https://github.com/tajpuriya27/active-browser/releases/latest/download/ActiveBrowser.app.zip`, which GitHub serves by redirect with no API involvement. All downloads use `curl -fsSL` (`-f` so an HTML 404 page is never mistaken for a zip).

Say plainly in the header comment that `ACTIVEBROWSER_ZIP`/`ACTIVEBROWSER_SUMS` exist so the install path can be exercised without a published release, and that the supported user-facing usage remains the §3 one-liner.

**D6 — Checksum verification: normalise the directory *and* the filename, then `shasum -a 256 -c` (`Project.md` §3 step 3).**
`make release` writes `SHA256SUMS` as a single line `<64 hex>  ActiveBrowser.app.zip` — a **bare** filename, because §5's recipe runs `cd build && shasum …`. So verification must run from a directory that contains a file of that exact name, or `shasum -c` reports the file as missing and fails. macOS's `shasum` is the Perl implementation and has **no `--ignore-missing`**, so there is no way to verify a subset.

Therefore: whichever path supplied them, copy/download the zip to `"$TMPDIR_WORK/ActiveBrowser.app.zip"` and the sums to `"$TMPDIR_WORK/SHA256SUMS"`, then

```sh
( cd "$TMPDIR_WORK" && shasum -a 256 -c SHA256SUMS )
```

wrapped in an explicit `if ! …; then fail "checksum verification failed …"; fi` so `set -e` cannot turn it into a silent abort. One code path for local and remote; a local zip under any name still validates, because it is the *bytes* that are hashed.

Policy when the sums file is absent: on the **remote** path it is a hard `fail` (§3 step 3 requires it — a release without its `SHA256SUMS` is a broken release). With `ACTIVEBROWSER_ZIP` set and no sums file found, print a prominent `warning: no SHA256SUMS next to <zip>; skipping verification` and continue, so the offline path stays usable. Never invent a third behaviour (e.g. computing and "accepting" the hash).

**D7 — Stage, validate, *then* replace. This is a deliberate refinement of §3 step 4.**
`Project.md` §3 step 4 reads "`pkill`; `rm -rf /Applications/ActiveBrowser.app`; `ditto -x -k` the zip into `/Applications`". Extracting straight into `/Applications` means the user's working app is already deleted when extraction runs; a truncated download that passed no checks, a full disk, or a zip whose top-level entry is not `ActiveBrowser.app` leaves them with **no** app and possibly a half-written bundle under a Launch Services record claiming `http`/`https` — a "never drop a URL" failure produced by the installer itself. The fix costs four lines and shrinks the destructive window to a local copy:

1. `ditto -x -k "$TMPDIR_WORK/ActiveBrowser.app.zip" "$TMPDIR_WORK/stage"`.
2. Validate the staged bundle, all **before** touching `/Applications`:
   - `[ -d "$TMPDIR_WORK/stage/ActiveBrowser.app" ]` — else `fail` naming what the archive actually contained.
   - `CFBundleIdentifier` is `com.local.activebrowser`, read with **`plutil -extract CFBundleIdentifier raw -o - …/Contents/Info.plist`**. The `-o -` is mandatory: without it `plutil -extract` **overwrites the plist in place** on this macOS and invalidates the signature (found twice already — task 03, and `tasks/00-current-status.md`).
   - Architecture: `lipo -archs "…/Contents/MacOS/ActiveBrowser"` must contain D4's corrected `$arch`; else `fail` with "this release is built for <archs>, this Mac is <arch>". v1 artefacts are single-arch by construction, so on an Intel Mac this refusal is the honest outcome — far better than installing an app that cannot launch and registering it as the system's `http` handler.
   - `codesign --verify --strict` on the staged bundle: **warning only, never a `fail`.** An ad-hoc signature carries no identity, so this is a structural check; the SHA-256 is the authenticity gate and it has already passed.
   - Read `CFBundleShortVersionString` (again `-o -`) for the progress output.
3. If `/Applications/ActiveBrowser.app` exists but its `CFBundleIdentifier` is **not** `com.local.activebrowser`, `fail` — never `rm -rf` an unrelated app that happens to share the name.
4. `pkill -x ActiveBrowser 2>/dev/null || true; sleep 1`. `pkill` must precede the `rm` (task 04 D2: do not pull a bundle out from under a live process, and `open` would otherwise merely re-activate the dying instance). The `sleep 1` is bounded process teardown and is **not** the scanner-race `sleep` task 04 D2a bans — say so in a comment so no reviewer confuses the two.
5. `rm -rf /Applications/ActiveBrowser.app` (mandatory: `ditto`/`cp` onto an existing bundle *merges*, and a stale `Contents/_CodeSignature/CodeResources` then fails `codesign --verify`, which macOS treats as "refuse to launch" — the same reason task 04 D2 gives), then `ditto "$TMPDIR_WORK/stage/ActiveBrowser.app" "/Applications/ActiveBrowser.app"`. `ditto` rather than `mv` because `$TMPDIR` may be on a different volume, and it preserves the signature and extended attributes.

Do **not** `lsregister -u /Applications/ActiveBrowser.app` before the `rm`. During the sub-second window between the `rm` and the `lsregister -f` the record points at a path that does not exist; unregistering as well would only widen the hole, and `make install` has carried the identical window since task 04.

**D8 — Register, launch, and inherit the single-record obligation (`Project.md` §3 step 5).**
`"$LSREGISTER" -f /Applications/ActiveBrowser.app` then **`open /Applications/ActiveBrowser.app`**, not `open -a ActiveBrowser`. §3 writes `-a`, but that is a *name* lookup through Launch Services and can in principle raise some other copy; the path form cannot, and it is what `make install` already does. Recorded deviation, same class as task 04's.

`install.sh` extracts to exactly one location and stages in a `mktemp -d` that no Launch Services scan indexes as an installed app, so it creates exactly **one** record — the obligation task 04 booked against this task. The script must never leave a second `.app` anywhere (no "backup copy" of the old bundle, no leftover staging directory — hence the `trap`).

Finish with §3 step 6: print the installed version and path, then the next step — open the menu bar item and choose **Set as Default Browser**. That hint is the last line on stdout.

**D9 — Quarantine: check, warn, never strip (`Project.md` §3 signing note, Verify step 5).**
`curl` does not set `com.apple.quarantine`, which is the entire reason an ad-hoc-signed bundle installs without notarization through this path. The script must **not** run `xattr -d -r com.apple.quarantine` — a blanket Gatekeeper-attribute strip is exactly the gesture an installer should not make, and it would hide the one case where it matters (a zip the user downloaded through a browser, which *is* quarantined). Instead, after staging, if the bundle carries the attribute, print `warning: the zip was obtained through a quarantining path; macOS may prompt on first launch`, and continue. `com.apple.provenance` is a different attribute and is expected on any locally copied app (task 04 saw it) — do not treat it as quarantine.

**D10 — The script touches the bundle and Launch Services, and nothing else.**
Forbidden inside `install.sh`: any `defaults` **write** (the `com.local.activebrowser` domain is the app's, and an installer that resets a user's browser choices is a bug), any `SMAppService`/`launchctl`/login-item manipulation, any change to the default-browser binding, `lsregister -kill` or `-r` (a system-wide database rebuild that transiently clears every app's handler bindings — banned for this run, see D11), `sudo`, `xattr -d`, and any write outside `$TMPDIR_WORK` and `/Applications/ActiveBrowser.app`.

Replace-in-place is what makes this safe: the path and bundle id are unchanged, so the `http`/`https` handler binding in `com.apple.launchservices.secure` and the `SMAppService.mainApp` login item both survive the swap, and the app's own launch-time logic (`AppDelegate.registerLoginItemIfInstalled()`, `App/AppDelegate.swift:127-161`) self-heals if macOS drops the Background Task Management record: it re-registers on `.notRegistered`/`.notFound`, does nothing on `.enabled`, and respects an explicit opt-out. **This is checked, not assumed** — Test Step 10 reads the `ActiveBrowser: login item:` line back and a `user` step confirms System Settings shows exactly one entry.

**D11 — Standing prohibitions that this task must honour, including one against `Project.md` itself.**
`Project.md` Phase 6 **Verify step 3** says to simulate a fresh machine with `lsregister -kill -r -domain local -domain user`. That command is **forbidden** for this run (it rebuilds the user's whole Launch Services database and transiently clears every app's handler bindings on a machine that is in the middle of a ten-PR test stack). Verify step 3 is therefore **out of scope, by name and with that reason**. The substitute this task does run is the honest part of it: `install.sh` itself deletes `/Applications/ActiveBrowser.app` and rebuilds the record from scratch with `lsregister -f` (Test Steps 7–9). What a genuinely pristine machine adds — no prior record, no `com.local.activebrowser` defaults domain — is not reproducible here without destroying state tasks 09/10 and the user's own PR testing depend on, so no `ai` step may `defaults delete com.local.activebrowser` either.

### Architectural notes and risks

- **The whole task turns on one inherited lesson: you cannot race the Launch Services scanner, so do not create the second bundle — or delete it.** `make release` is the third target to face it (`install` was the first, `clean` the second by accident). Any *future* target or script that materialises a second `com.local.activebrowser` bundle inherits the same obligation and the same answer.
- **`make release` no longer leaves an inspectable `build/ActiveBrowser.app`.** That is a real ergonomic cost, accepted for the same reason task 04 accepted it: `make bundle` regenerates it in ~0.3 s, and doing so knowingly re-creates the duplicate record until the next `install`/`release`/`clean`. Consequence for testing: **do not run `make bundle` or `make run` between Test Step 5 and the `user` dropdown step**, or the second row returns by design.
- **Single-arch artefacts are the biggest v1 distribution gap.** `swift build -c release` produces a binary for the builder's architecture only, so a v1 release cut on Apple silicon cannot run on an Intel Mac. D7's `lipo -archs` check converts that from "installs, then never launches, while holding the `http` handler" into an explicit refusal. **Follow-up for task 10's planner (not this PR):** either build universal (`swift build --arch arm64 --arch x86_64`, or two builds + `lipo -create`) in `release.yml`, or state arm64-only support on the Release page. `Project.md` §3's "arm64 or x86_64 **as built**" is the sentence that anticipates this.
- **`install.sh` is not reviewed by a compiler.** There is no XCTest target and shell has no type checker, so the acceptance criteria lean on `bash -n`/`sh -n`, the three negative Test Steps, and the two idempotent positive runs. The three classic `curl | sh` failure modes are each pinned to a decision: unset-variable abort (D3, `${VAR:-}`), silent death on a non-matching `grep` under `pipefail` (D3, `|| true` + explicit check), and stdin collision with a prompt (D3, no `read`).
- **The destructive window is unavoidable but is now ~1 s and purely local.** Between `rm -rf /Applications/ActiveBrowser.app` and `lsregister -f`, the user's `http` handler names a path that does not exist; a link clicked in that instant is dropped. D7's staging removes every *network* and *validation* failure from that window (nothing can fail in it except a local `ditto`), which is the most that replace-in-place allows. `make install` has carried the identical window since task 04.
- **`shasum` on macOS is Perl's and lacks `--ignore-missing`**, so `shasum -c` fails if the sums file names any file that is not present. D6's normalisation into one temp directory keeps that from ever mattering; if task 10 ever publishes a multi-file `SHA256SUMS`, this script must be revisited. Flag it to task 10's planner: **keep `SHA256SUMS` to the single `ActiveBrowser.app.zip` line.**
- **The GitHub API path is the least testable part of this task** and is deliberately the thinnest: one grep for `tag_name`, a deterministic asset URL, and a no-API fallback. It cannot be exercised by an `ai` step here (the repo may still be private and task 10 has not published a release), so it is reviewed by inspection and proved for real in task 10. Do not let it grow features it cannot be tested for.
- **`gh` cannot help here either:** this machine's active `gh` account is `sunil-phil` and cannot resolve `tajpuriya27/active-browser`; anything needing the API would require `GH_TOKEN=$(gh auth token --user tajpuriya27)`. `install.sh` must not shell out to `gh` — a stranger's machine does not have it.
- **Replace-in-place preserves the two pieces of system state that took a PR each to establish** (the default-browser binding from task 05, the login item from task 06), because neither is keyed on the bundle's contents. This is asserted rather than assumed: a dangling login item would be a genuine regression in the product's least visible corner, and the `ai` step reads it out of the app's own `NSLog` line — `NSLog` does not reach `log show` on this machine, so the binary must be run directly, killed, then relaunched with `open`.
- **Quarantine is the one Gatekeeper property the whole v1 distribution story rests on** (`curl` does not set it; browser downloads and Homebrew do). D9's warn-don't-strip rule keeps that property observable instead of papering over the case where it is violated. When a browser-download or Cask path is added later, `make sign` + `make notarize` land **first**, per `Project.md` §3.
- **`build/ActiveBrowser.app.zip` and `build/SHA256SUMS` are untracked build output** in a repo that still has no `.gitignore` (flagged since task 01). The git-agent stages `Makefile`, `install.sh` and the task file **by explicit path**; `git add -A` would commit a 2 MB zip.
- **Task 10 consumes this task's output and must not re-litigate it.** Its workflow runs `make release` on `macos-latest` and uploads `build/ActiveBrowser.app.zip` + `build/SHA256SUMS` with `gh release create`. It must **not** run `make install`, must not add Launch Services calls, and gets the universal-binary question above.

1. **Three helpers, not two.** D3 specifies `fail()` plus one progress printer; `warn()` is the third because D4 (missing `lsregister`), D6 (missing sums on the local path) and D7/D9 (`codesign --verify` and quarantine) all mandate "warn and continue". `fail` and `warn` write to stderr, `say` (the single progress printer, `==> …`) to stdout, which keeps the *Set as Default Browser* hint the last line **on stdout** even when a warning fires.

The header says "no privilege escalation of any kind" and the `/Applications` refusal uses D4's own wording, "install as an admin user". 4. **Tag parsing is two statements, not one pipeline**: `grep -o '"tag_name"[[:space:]]*:[[:space:]]*"[^"]*"' | head -1 || true`, then a separate `sed 's/.*"\([^"]*\)"$/\1/' || true`. Splitting keeps each `|| true` unambiguous under `pipefail` and makes the empty-tag case fall through to the no-API `releases/latest/download/` redirect with a printed note, exactly as D5 requires. No `browser_download_url` parsing.
5. **The quarantine check is on the *staged* bundle** (D9's "after staging"), before it is copied, because `ditto` preserves extended attributes — so the staged copy answers the question for the installed one. `xattr -p com.apple.quarantine` is guarded with `|| true`; `com.apple.provenance` is never consulted.
