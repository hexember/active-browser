# Task 04 — make install: copy to /Applications and register with Launch Services

Status: pr-open
Phase: 3
Branch: feature/make-install
Base: feature/bundle-makefile
PR: https://github.com/hexember/active-browser/pull/6
Created: 2026-09-20

## Goal
Add the `install:` target to the existing `Makefile` so the bundle is copied to `/Applications` and force-registered with Launch Services, and so the now-redundant `build/ActiveBrowser.app` is **deleted and unregistered** immediately after the copy — leaving nothing on disk for the Launch Services scanner to rediscover, and therefore exactly one `com.local.activebrowser` record. The result is that ActiveBrowser appears **once** as an eligible choice in System Settings → Desktop & Dock → *Default web browser*. One target, one existing file, no new files, no Swift.

## Spec (planner)

### Decisions to read before writing anything

**D1 — This task adds exactly one target to one existing file.** `Makefile` gains an `install:` target and one word in `.PHONY`. Nothing else in the repo changes: no new files, no `Sources/`, no `Package.swift`, no `Support/Info.plist`, no `.gitignore`, no `install.sh`, no `.github/`. Task 03's Makefile comment already states that any later target *must* be added to `.PHONY`; this task is the first to exercise that instruction.

**D2 — The recipe (amended by re-plan #2, 2026-09-20; one line added relative to `Project.md` §5, and the `-u` moved).** Reproduce this exactly, in this order — **seven** recipe lines:

```make
install: bundle
	-pkill -x $(APP)
	rm -rf /Applications/$(APP).app
	cp -R $(BUNDLE) /Applications/
	rm -rf $(BUNDLE)
	-$(LSREG) -u $(BUNDLE)
	$(LSREG) -f /Applications/$(APP).app
	open /Applications/$(APP).app
```

Differences from `Project.md` §5: one **new** line, `rm -rf $(BUNDLE)`, and `-$(LSREG) -u $(BUNDLE)` moved from line 2 to sit immediately after it. Everything else is §5 verbatim, same flags, same leading `-`s. D2a is the evidence and is mandatory reading; the implementer must not reorder, merge or "simplify" anything else.

Line-by-line justification:

| Line | Why it is there, and why *here* |
|---|---|
| `install: bundle` | Guarantees `build` → `bundle` → `codesign` ran, so `/Applications` can never receive a stale or unsigned bundle. Never install from a hand-assembled directory. Yes, this target now deletes its own prerequisite's output — see the `rm -rf $(BUNDLE)` row; that is intentional and is the whole fix. |
| `-pkill -x $(APP)` | **Must be first.** Four reasons now: (a) the `open /Applications/ActiveBrowser.app` line would otherwise merely *activate* an already-running instance of the same bundle id instead of launching the new binary — the trap task 03 D3 documented for `make run`; (b) `rm -rf /Applications/ActiveBrowser.app` must not pull a bundle out from under a live process; (c) **nor must `rm -rf $(BUNDLE)`** — after `make run`, the *build* copy is the live process, and this line is the only thing that stops the new `rm` from deleting a running app's bundle; (d) a running app is continuously re-registered by Launch Services, so `-u` against the path of a live process is undone immediately. Leading `-` because `pkill` exits `1` when nothing matches and `make` would otherwise abort — `make: [install] Error 1 (ignored)` is the expected, correct output on a cold machine. |
| `rm -rf /Applications/$(APP).app` | `cp -R src dest/` onto an **existing** bundle merges trees instead of replacing them: files removed since the last version survive, and a stale `Contents/_CodeSignature/CodeResources` makes `codesign --verify` fail, which on macOS means the app is refused at launch or killed. Deleting first makes `make install` idempotent and is the upgrade path Phase 6's `install.sh` mirrors. **No leading `-`:** if the old copy cannot be removed we must stop, not install a half-merged bundle. (`rm -rf` on a missing path already exits `0`.) |
| `cp -R $(BUNDLE) /Applications/` | Plain copy of the freshly signed bundle. **No `sudo`** — `/Applications` is writable by an admin user; a permission error is a `[RE-PLAN REQUEST]`, never a reason to add `sudo`. No leading `-`; it must abort here rather than continue to the next line and delete the source of a copy that did not happen. If `codesign --verify --strict` on the installed copy fails (Test Step 7), that is the signal to escalate and switch to `ditto` — do not change it pre-emptively. |
| `rm -rf $(BUNDLE)` | **The duplicate-registration fix (new line, re-plan #2).** As long as a second `.app` declaring `com.local.activebrowser` sits on disk under the repo, the Launch Services background scanner **will** register it — measured ~3 s *after* `make install` has already returned and exited, so no placement of `lsregister -u` inside the recipe can beat it (D2a, measurement 1). Deleting the bundle removes the *cause* rather than racing the *effect*: with nothing on disk, no later scan can create the record. Placed immediately after `cp -R` — the instant the build copy has served its only purpose — so that (i) the destructive step is adjacent to the copy that made it redundant, and (ii) it precedes the two un-`-`'d lines that can abort the recipe, so an abort can never leave a live duplicate behind. **No leading `-`:** if the build copy cannot be deleted, the single-record invariant is broken and that must be loud. Note this deletes only `build/ActiveBrowser.app`; the `build/` directory and `.build/` remain for `make clean`. |
| `-$(LSREG) -u $(BUNDLE)` | Sweeps up the record the scanner may **already** have created for the build copy before the `rm` — from a previous `make run` (Test Step 4), or from a scan that fired while `bundle:`/`cp -R` were running. The `rm` stops new records appearing; this removes any that exist. **Must come after the `rm`**, not before: run first, it would leave a window in which the bundle is still on disk and a fresh scan could re-register it. Leading `-`: there is frequently no record to remove and `lsregister -u` exits non-zero then — `make: [install] Error 1 (ignored)` is correct output and `make` still exits `0`. **Only the `build/` path is named**; `-u` is path-scoped, so the `/Applications` record sharing the bundle id is unaffected. |
| `$(LSREG) -f /Applications/$(APP).app` | The point of the whole target. Without it Launch Services learns about the new path only lazily, so ActiveBrowser would not show up in the *Default web browser* list until some later scan. `-f` forces the record to be (re)read from disk, which is what makes the second install pick up a changed `Info.plist`. Must come **after** `cp -R` (registering a path that does not exist is meaningless) and **before** `open` (so the schemes are indexed deterministically rather than depending on the app's own launch-time registration). It is deliberately **after** the `rm`/`-u` pair so that the only registration work left at this point concerns `/Applications`. **No leading `-`** — this failing means the task did not do its job and must be visible. |
| `open /Applications/$(APP).app` | Leaves the installed agent running, and makes Launch Services record the running instance as the `/Applications` copy. Safe as the last line only because line 1 killed any same-id instance. Nothing after it needs to run, which is now a property rather than an accident: the single-record invariant is already established by the time `open` is reached. |

**D2a — Why the build copy is deleted, not merely unregistered. (Rewritten by re-plan #2; supersedes re-plan #1, which chose option (a) and was wrong.)**

*The defect.* `Project.md` §5 lists `-$(LSREG) -u $(BUNDLE)` as the second line of `install:`. It does not work, and — the finding that forced this second re-plan — **no position inside the recipe works.** Authoritative measurement (main session, on this machine, Darwin 25.6 / macOS 26), taken with the re-plan #1 recipe in place, i.e. with the `-u` already moved to the very last line after `open`:

```
baseline build-path records: 0
make install  -> exit=0, wall time 1.76s
T+0s  : build-path records = 0
T+3s  : build-path records = 1
T+6s  : 1    T+10s : 1    T+20s : 1    T+40s : 1
```

The whole target runs in **1.76 s**; the scanner registers `build/ActiveBrowser.app` about **3 s after `make install` has already returned**, and the record then persists indefinitely. The final `-u` therefore removes nothing — it executes before the record it is meant to delete exists. Re-plan #1's premise ("the recipe tail buys enough elapsed time") is false: the recipe has no tail worth speaking of. Earlier contrary datapoints are explained, not contradicted: a `-u` *typed by hand* seconds after the target finished does land after the scan and does stick, which is why the reviewer's manual mitigation appeared to work and why the implementer saw the duplicate appear only "15–20 s later".

*The corrective measurement.* Deleting the bundle closes it, and does so categorically rather than by winning a race:

```
before: 1
rm -rf build/ActiveBrowser.app ; lsregister -u build/ActiveBrowser.app
T+0s : 0    T+5s : 0    T+10s : 0    T+20s : 0    T+40s : 0
```

The mechanism is the point: **the scanner registers what is on disk.** Once `build/ActiveBrowser.app` does not exist, there is no later scan that can recreate the record, whatever the timing. Note the two commands were measured as a pair, so which of them removed the pre-existing record is not established — both stay in the recipe and nothing depends on knowing.

*The options, re-judged against that evidence.*

| Option | Verdict |
|---|---|
| **(a) Move `-u $(BUNDLE)` after `open`** | **Rejected — measured not to work** (measurement 1 above ran *with* this recipe). It is a timing fix for a problem whose timing we do not control. |
| **(b) Keep the §5 `-u` and repeat it after `open`** | **Rejected.** Two losing lines instead of one: both fire inside a 1.76 s window, the scan lands ~3 s later, so neither can remove the record. |
| **(c) `rm -rf $(BUNDLE)` then `-u`, immediately after `cp -R`** | **CHOSEN.** The only option measured to hold (stable at 0 through T+40 s), and the only one whose correctness does not depend on a timing constant. Order is load-bearing: the `rm` first, so no new record can be created; the `-u` after it, to sweep any record that already existed. Placed right after `cp -R` rather than at the end of the recipe so that both lines complete *before* the two un-`-`'d commands (`lsregister -f`, and any failure in `open`) that could abort the target — an abort must not be able to leave a registered-but-deleted build path behind. |
| **(i) Accept the duplicate; rely on task 05 binding by explicit URL** | **Rejected**, though it is the closest call. The supporting fact is real: `Project.md` §5's menu action is `setDefaultApplication(at: Bundle.main.bundleURL, …)`, which binds the URL of the **running** copy — always `/Applications/ActiveBrowser.app` — and never does a bundle-id lookup, so *our own* code cannot bind the handler role to `build/`. `BrowserRegistry` is also safe: it filters on `Bundle.main.bundleIdentifier`, which both copies share, so neither can be routed to and there is no loop risk (guardrail §1). What remains is a second ActiveBrowser row in the System Settings *Default web browser* dropdown — and that dropdown is exactly where this task's `user` step, `Project.md` Phase 3 Verify step 4, and the Reset block all send the human. A user who picks the wrong identical-looking row binds the system default browser to a path that the next `make clean` deletes: clicked links then resolve to nothing. That is the "Never Drop a URL" class failure (guardrail §1) reachable by a plausible click, so accepting it means shipping a foot-gun into the one UI we ask the user to operate. (c) removes the row entirely for one added line. |

*Re-judging re-plan #1's objections to (c)* — the main session's analysis is accepted on all three:
- *"`make clean`'s `-u $(BUNDLE)` becomes a permanent no-op after any install"* — true and harmless. It already carries a leading `-`, `clean` still removes `.build/` and `build/`, and task 03's "unregister exactly what you are about to delete" rationale still has a live subject: the `make bundle` / `make run` path, which is the case it was written for and where `build/ActiveBrowser.app` does exist at `clean` time.
- *"you cannot diff built vs installed when debugging"* — overstated. `make bundle` recreates `build/ActiveBrowser.app` in ~0.3 s on demand; the cost is one command, not the capability.
- *"task 09's `release:` silently re-assembles"* — a non-issue: `release:` depends on `bundle:`, which unconditionally `rm -rf`s and rebuilds the bundle anyway, so its behaviour is identical whether or not an install deleted it first. **To confirm when task 09 is planned**, along with the matching obligation that `release:`/`install.sh` leave no second registered copy.

*The bounded property this leaves.* `make install` and `make clean` both end with exactly one record. `make bundle` and `make run` deliberately create the build copy, so from ~3 s after either of them until the next `install`/`clean` there are **two** records — inherent to having a second bundle on disk, true of every option above, and confined to explicit developer commands. The user-facing paths (`make install` now, `install.sh` in Phase 6) never leave a duplicate. Practical consequence for testing: **once Test Step 11 has passed, do not run `make bundle` or `make run` again before the `user` dropdown step**, or the duplicate row comes back by design.

*Status of the deviation.* A **deliberate, recorded deviation** from the `Project.md` §5 listing — now an added line, not just a moved one — and not an orphan implementation. §5 is titled *Code Skeleton*: a sketch of the targets, not a normative recipe. §3 Phase 3 states the actual *requirement* ("`make install` should `lsregister -u build/ActiveBrowser.app` first", so `setDefaultApplication` cannot bind to the build copy); this recipe delivers that requirement's stated purpose — one record, never the build path — which the §5 recipe provably does not on macOS 26. The approved specification for this task is this Spec. Two obligations follow: the Makefile comment must record the deviation and its measured reason (checklist item 3), and `Project.md` §5 + §3's wording should be corrected in a later docs-only task — **not** in this PR, which stays Makefile-only.

*What is explicitly not allowed as a fix.* **No `sleep` in the recipe** — re-plan #1 banned it as unnecessary; re-plan #2 bans it as insufficient as well, since the scan lands after the target returns and "sleep until it's safe" is an unbounded guess that slows every install. No `lsregister -kill`/`-r`. No hand-run `lsregister -u` as a standing mitigation. If Test Step 11 fails, that is a `[RE-PLAN REQUEST]`.

**D3 — `clean` is NOT changed by this task, and specifically must NOT unregister the installed copy.** Two separate questions, both answered "no change":

1. *Should `clean` pkill?* No — task 03 D3 stands, and this task is exactly why. From now on `make clean` can be run while the user's **installed** agent is running; from task 05 it may be the default browser and from task 06 a login item. Deleting build artefacts must never kill the user's menu-bar agent as a side effect. Killing stays an explicit act (`pkill` now, the Quit item from task 07).
2. *Should `clean` also run `$(LSREG) -u /Applications/ActiveBrowser.app`?* **No.** `clean`'s existing `-u $(BUNDLE)` exists to honour one invariant: *unregister exactly what you are about to delete*. `clean` deletes `.build/` and `build/`; it does not delete `/Applications/ActiveBrowser.app`. Unregistering a bundle that still exists on disk inverts the invariant and is actively harmful: after task 05 the user's `LSHandlers` entry still names `com.local.activebrowser` while its only registration record is gone, so clicked links resolve to nothing until Launch Services happens to re-index — a silent, nondeterministic URL-dropping failure caused by a routine developer command. Leave `clean` byte-for-byte as task 03 shipped it. **And note `clean` does not suffer the D2a race**, despite running its `-u` *before* its `rm -rf`: the recipe deletes `build/` and never re-creates it, so once `clean` finishes there is nothing on disk for the scanner to find. That is the same mechanism this task's new `rm -rf $(BUNDLE)` line imports into `install:` — which is why `clean` needs no change.
3. *Should this task add an `uninstall:` target instead?* **No — out of scope.** `Project.md` §5 lists the target set (`build`, `bundle`, `install`, `run`, `release`, `clean`); `uninstall` is not in it, so adding one is a change outside the approved specification (guardrail §3, *No Orphan Implementations*) and would need `Project.md` amended first. **D2a is not a precedent for this**: that deviation reorders two existing lines of one listed target to make it meet a requirement `Project.md` §3 itself states, and is evidence-backed and recorded; adding a target introduces behaviour `Project.md` never specified. Reordering an approved recipe to make it work ≠ inventing a new target. The teardown sequence is documented instead, by hand, in this task's **Reset** block — which is also the only place that needs it, since it runs once at the end of the whole PR stack.

**D4 — This task deliberately leaves system state behind.** At the end of `make install` there is a real app in `/Applications` and a running agent with **no menu bar item and no Quit** (task 07) — `pkill -x ActiveBrowser` is still the only stop switch. Tasks 05–08 all test against that installed copy, so the Reset block must **not** be run between tasks; see the Test Steps.

### Architectural notes and risks

- **Why this is the first task with a real Launch Services footprint.** Task 03 registered the build copy transiently and unregistered it in `clean`. From here on a record survives every `make clean`, which is the whole point (task 05 needs a stable, installed handler to make default) and also the reason the Reset block is end-of-stack rather than per-task.
- **Two paths, one bundle id — the central hazard.** Everything in D2's `rm -rf $(BUNDLE)` + `-u` pair and in Test Steps 4/10/11 exists for this. Any future target that leaves a second copy of `com.local.activebrowser` on disk (Phase 6's `install.sh`, a `release` zip that someone double-clicks and then keeps) inherits the same obligation — and the same conclusion: remove the copy, do not try to out-run the scanner.
- **The generalisable lesson: you cannot race the Launch Services scanner, so do not try.** It registers what is **on disk**, on macOS's schedule, ~3 s after the file appears and well after a sub-2-second `make` target has exited. Every timing-based mitigation (`-u` earlier, `-u` later, `-u` twice, `sleep`) is therefore unsound by construction; the only sound mitigations are *don't create the second bundle* or *delete it*. Corollary for every future test step: assertions about registration state are taken after a settling delay, never on return.
- **Why `make clean` needs no equivalent change.** It runs its `-u` *before* its `rm -rf`, which would be the wrong order here — but `clean` deletes `build/` and never re-creates it, so once it finishes there is nothing on disk to rediscover. Same mechanism, arrived at by accident; leave it alone (D3).
- **Ordering inside the new pair is load-bearing.** `rm` then `-u`, not the reverse: the `rm` closes the source of new records, the `-u` clears any already created. Reversing them reopens a window in which the bundle is still on disk and a scan can re-register it. Placing the pair before `$(LSREG) -f` (which has no leading `-` and can abort the recipe) means an abort cannot strand a registered build path.
