## Goal
Give ActiveBrowser its menu bar surface: an `NSStatusItem` whose menu shows the live routing target (*Routing to:*) and the LRU order (*Recent:*), rescans the registry on `menuWillOpen`, and carries the three action items *Set as Default Browser*, *Launch at Login* and *Quit*. It also closes task 06's hand-off defect by adding a persisted `launchAtLoginOptOut` flag so a Launch-at-Login toggled **off** from this menu is not silently re-enabled at the next launch.

## Spec (planner)

### Decisions to read before writing code

**D1 — Scope fence: this task is the status item and the three action items only.**
`Project.md` §5's Phase 5 menu sketch has five item groups. The *Browsers* include/exclude submenu and the *Fallback Browser* radio submenu are **task 08** (`Project.md` §3 task table) and must not appear in this diff — no `toggleBrowser(_:)`, no `chooseFallback(_:)`, no `NSMenuItem.submenu`, no mutation of `settings.includedBrowsers` or `settings.defaultBrowser`. This task leaves a single marker comment at the insertion point so task 08 is a pure insertion (the same contract task 02 D3 gave this task).

**D2 — `URLDispatcher.resolvedTargetId()` is the only source of the *Routing to:* name. Do not re-derive resolution.**
Task 02 built that seam for exactly this (`Core/URLDispatcher.swift:46-52`). `MenuBarManager` must never call `stack.resolveTarget(fallback:)`, never read `settings.defaultBrowser` as a display fallback, and never re-implement the candidate walk. If the menu and the dispatch could disagree, the menu becomes a liar and every future routing bug gets debugged against the wrong number. The bundle id returned is turned into a display name with `registry.entry(for:)?.name ?? id` and nothing else; `nil` renders as `Routing to: none`.

**D3 — The login-at-login opt-out (the subtle part of this task; read task 06's hand-off note at `tasks/06-launch-at-login.md:101`).**
`SMAppService.mainApp.unregister()` leaves the status at `.notRegistered(0)` or — on this macOS — `.notFound(3)`. Task 06's launch gate registers on **both**. So a user who switches Launch at Login off from this menu would find it back on at the next launch, with no way to tell why. The fix belongs here, with the UI that creates the ambiguity:

- New persisted key **`launchAtLoginOptOut`** (`Bool`, domain `com.local.activebrowser`), defined in `Core/Settings.swift`. Absent ⇒ `false` ⇒ task 06's behaviour is unchanged for every existing user (`UserDefaults.bool(forKey:)` returns `false` for a missing key — this is the reason a plain `Bool` is right and an `Optional<Bool>` is not).
- **Exactly one writer:** `MenuBarManager.toggleLaunchAtLogin()`. It sets `true` on the off-path (before calling `unregister()`) and `false` on the on-path (before calling `register()`). Nothing else in the codebase writes it — not `AppDelegate`, not bootstrap seeding.
- **Exactly one reader:** `AppDelegate.registerLoginItemIfInstalled()`, as a new branch inserted **between** the `/Applications/` path gate and the `SMAppService.Status` switch:

  ```
  if !Bundle.main.bundleURL.path.hasPrefix("/Applications/") {
      message = "skipped, bundle is not under /Applications (…)"       // unchanged
  } else if settings.launchAtLoginOptOut {                             // NEW
      message = "skipped, user opted out (launchAtLoginOptOut=true)"   // NEW, exact string
  } else {
      … the existing status switch, byte-for-byte unchanged …
  }
  ```
  Written this way the change is an **insertion of two lines** — no pre-existing line of that function is edited, and the single-`NSLog` contract (task 06 D3) still holds because the new branch only assigns `message`. The message string is **literal and load-bearing**: Test Step 4 greps for it.
- The opt-out gate deliberately sits **before** the status switch, so it wins over `.notRegistered`/`.notFound` exactly as task 06 required ("treat `.notFound` exactly like `.notRegistered` — 'no record exists' is not evidence that the user wants one, once an explicit opt-out is possible").
- **The menu checkmark is derived from `SMAppService.mainApp.status`, never from the flag.** If `unregister()` throws, the flag is set but the login item still exists; a checkmark driven by the flag would show "off" while macOS still launches us. Status is the truth; the flag only governs *our* auto-registration.

**D4 — The focus-change hook on `FocusObserver` is a closure property, and it must capture `[weak self]`.**
`FocusObserver` has no callback today by design (task 02). Add `var onFocusChange: (() -> Void)?`, invoked as the **last** statement of `appActivated(_:)`, after `stack.touch(id)` and inside the same `guard` (so it fires only for an included browser that actually changed the stack). `AppDelegate` wires it:

```swift
focusObserver.onFocusChange = { [weak self] in self?.menuBar?.refresh() }
```

`[weak self]` is **mandatory**: `AppDelegate` owns `focusObserver` non-optionally, so a strong capture of `self` gives `AppDelegate → FocusObserver → closure → AppDelegate`, a retain cycle. It leaks nothing visible here (the delegate lives for the whole process), but it is the wrong shape to hand to task 08 and a reviewer will — correctly — reject it.

Rejected alternative, and why: **do not** have `MenuBarManager` register its own `NSWorkspace.didActivateApplicationNotification` observer. It would be a second observer for the same event (`Project.md` Phase 2 Verify asserts exactly one), it would duplicate the `includedBrowsers` filter, and observer invocation order is unspecified — the menu could read the stack *before* `FocusObserver` touched it and display the previous browser. The closure guarantees ordering.

**D5 — Status item presentation: template icon, no text title; the name lives in the tooltip and on the first menu line.**
`Project.md` §5 sketches `[Icon: current target name]`. A live text title is the wrong call here: target names run from `Arc` to `Google Chrome Canary`, so a variable-width item makes the entire right-hand menu bar shift on every focus change, and on a notched display it pushes items into the hidden overflow. Ship `NSImage(systemSymbolName: "globe", accessibilityDescription: "ActiveBrowser")` with `isTemplate = true` (template so it inverts correctly in dark mode and while the menu is highlighted), and put the live name in `button.toolTip` and the accessibility description, refreshed by `refresh()`. The authoritative, always-visible statement of the target is the *Routing to:* line, one click away. **Safety rule:** if `NSImage(systemSymbolName:…)` returns `nil`, fall back to `button.title = "AB"` — a status item button with neither image nor title is zero-width and unclickable, i.e. an app the user cannot quit.

**D6 — *Set as Default Browser* calls `setDefaultApplication` for `"http"` only, and the `https` binding is a measurement, not an assumption.**
macOS treats `http`+`https` as one "default web browser" role: the System Settings control and the confirmation dialog set both. Issuing a second call for `"https"` risks a second confirmation dialog for one user intent, and sequencing it inside the first call's completion handler drags an `@Sendable` async hop into an otherwise fully synchronous `@MainActor` codebase. So: one call, `scheme = "http"`, exactly as `Project.md` §5 specifies. Test Step 12 then reads `LSHandlers` and asserts **both** `http` and `https` bind `com.local.activebrowser`. If only `http` binds, that is a recorded finding and a pre-registered follow-up `fix/` task (add the `https` call from the completion handler) — not a re-plan of this one.
Use the completion-handler form and log a non-`nil` error. The handler is `@Sendable`: it must capture **nothing** (no `self`, no menu item) and do nothing but `NSLog`.

**D7 — *Quit* is `NSApp.terminate(nil)`, and it changes every later reset block.**
Until now `pkill -x ActiveBrowser` was the only stop switch (task 05 note). From this task on, the supported way to stop the agent is the menu. Two consequences to write down rather than discover: (a) `Quit` does **not** remove the login item and does not undo the default-browser binding — the reset blocks still own those; (b) once ActiveBrowser is the default handler, macOS relaunches it on the next link click (task 05 Verify 8), so "quit" means "until the next link", which is correct agent behaviour and must not be "fixed".

### Architectural notes and risks

- **`NSMenuItem.target` is a weak reference, and so is `NSMenu.delegate`.** Checked: AppKit declares both as weak (`NSMenuItem.target` has been zeroing-weak since 10.6; `NSMenu.delegate` is `weak var`). This is not a stylistic note — it decides the design. If `MenuBarManager` were created as a local in `applicationDidFinishLaunching` and not stored, the status item would still appear (the `NSStatusBar` retains the item, and the item retains the menu), the menu would still drop down, and **every click would silently do nothing** while `menuWillOpen` never fired. Hence checklist item 4.1: `AppDelegate` must hold it in a stored property for the process lifetime, which it gets via the entry point's `withExtendedLifetime(delegate) { app.run() }`.
- **The `NSStatusItem` must also be retained.** Releasing it removes the item from the menu bar; holding it in a `let` on `MenuBarManager` (itself retained by `AppDelegate`) is the whole lifetime story. Never call `NSStatusBar.system.removeStatusItem(_:)`.
- **No polling anywhere.** The menu's contents are computed at two event-driven moments only: `menuWillOpen` (user action) and `onFocusChange` (system notification). `SMAppService.mainApp.status` is read inside `rebuild()`, i.e. on menu open, not on a timer. Guardrail §1 holds.
- **`refresh()` cost.** It calls `dispatcher.resolvedTargetId()` on every activation of an *included* browser. That walks the candidate list and stops at the first hit, doing one `NSRunningApplication` query plus one `urlForApplication` + `fileExists` — bounded, on the order of a handful of calls, and driven by human-paced focus changes. This is within guardrail §2's "no unbounded file I/O on the main thread"; `registry.refresh()` (the real Launch Services scan) stays on the menu-open path only.
- **Ad-hoc signing may make `unregister()` throw**, same risk class task 06 flagged for `register()`. If it does, the flag is already persisted, so the next launch will not re-register — but the existing login item stays until the user removes it in System Settings. The menu will show this honestly, because the checkmark reads `status`, not the flag (D3). Record the logged error and raise a follow-up; it is not a re-plan of this task.
- **`.requiresApproval` is a real state on this machine.** Task 06's reset instructs the user to switch the login item *off* in System Settings, which leaves `.requiresApproval(2)`. If the human did that before testing this task, the *Launch at Login* item will show a dash (mixed) and clicking it opens System Settings instead of toggling. That is the designed behaviour, not a failed step — the `user` step below says so explicitly.
- **`setDefaultApplication`'s completion handler is `@Sendable` and non-isolated.** Capturing `self` (a `@MainActor` class) there is a Swift 6 error or a concurrency warning; capturing an `NSMenuItem` is worse. Capture nothing. This is the one place in this task where the compiler will push back if the rule is broken, which is exactly why the rule is cheap to follow.
- **`defaults write` while the app is running is a footgun.** `UserDefaults`/`cfprefsd` caching means a running process may not observe an external write, and a subsequent in-process write can clobber it. Every `ai` step that manipulates `launchAtLoginOptOut` must **kill the app first, write, then launch** — the steps below are ordered that way deliberately.
- **`NSLog` does not reach `log show` on this machine (task 06 D6, measured).** Every log observation runs the bundle's executable directly and captures stderr, then kills it and relaunches with `open -a ActiveBrowser`. Do not add a second log sink to work around this.
- **Menu bar crowding / notch.** On a notched display with many menu bar items, macOS can hide the item entirely. If the `user` cannot find it, that is an environment condition, not a code defect — have them check with a wider window arrangement or Bartender-style overflow before recording a failure. D5's fixed-width icon reduces, but does not eliminate, this.
- **`menuWillOpen` rescan is only partially observable in this task.** `registry.refresh()` affects display names and — from task 08 — the *Browsers* submenu's membership. Proving "a newly installed browser appears" needs a browser installation, which is out of proportion here; `user` step 8 proves the rebuild-on-open path runs (the lines change between opens without a relaunch), and task 08 inherits the new-browser-appears check. Do not simulate it by planting a fake `.app` that claims `https` — that would pollute the user's Launch Services database and the default-browser dropdown.
- **`Project.md` Phase 4 Verify step 1 and step 7's "off" half land here.** Task 05 D1 deferred the *Set as Default Browser* menu action to this task, and task 06 D5 deferred the *toggle Launch at Login off from the menu* half. Both are carried as `user` steps 9 and 10 below. Nothing else from Phase 4 is re-run.
