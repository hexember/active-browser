# Task 06 — Launch at Login via SMAppService with /Applications gate

Status: pr-open
Phase: 4
Branch: feature/launch-at-login
Base: feature/set-default-routing
PR: https://github.com/hexember/active-browser/pull/8
Created: 2026-09-21

## Goal
Make ActiveBrowser register itself as a login item on first launch, so the agent is already running and observing focus before the first link of the day is clicked — but only when it is running from `/Applications/`, so a dev build in `build/` can never leave a login item pointing at a deleted path. The registration gate is decided **per `SMAppService.Status` case** (D4), which is a deliberate, measured deviation from `Project.md` §5's `status == .notRegistered` sketch. One file changes: `Sources/ActiveBrowser/App/AppDelegate.swift`.

## Spec (planner)

### Decisions to read before writing code

**D1 — Auto-registration only. No `LoginItem` helper type, no menu UI, no `unregister()` anywhere in this task.**
`Project.md` §5 puts `SMAppService.mainApp.register()/.unregister()` directly in two places: the gated block in `applicationDidFinishLaunching` (this task) and `MenuBarManager.toggleLaunchAtLogin()` (task 07). §4's directory structure has **no** file for a login-item helper, so creating `Core/LoginItem.swift` would be a §4 deviation and, per guardrail §3's re-plan protocol, would need escalation rather than a planner's convenience. A helper type would also have exactly one caller until task 07 exists — guardrail §3, *no orphan implementations*. Task 07 calls `SMAppService` directly, exactly as §5 shows. **Decided: minimal, inline, one file.**

**D2 — `try?` is replaced by `do/catch` + one log line. This is the substantive deviation from §5 and it is deliberate.**
`try? SMAppService.mainApp.register()` makes the single most failure-prone call in the app completely silent. The realistic failure modes here are not theoretical: the bundle is **ad-hoc signed** (`Makefile:19`, `codesign --sign -`), and Background Task Management can refuse or defer registration for a bundle whose signing identity it does not trust, with the failure surfacing only as a thrown error. With `try?`, the symptom on this machine would be "the `user` step says nothing appears in Login Items" and no evidence of why. Task 02 set the precedent for exactly this situation: `Core/URLDispatcher.swift` `NSLog`s its one unrecoverable path instead of failing mutely.

The failure is also **not** recoverable in code — there is nothing to retry and nothing to show the user (there is no UI until task 07) — so the correct handling is: log, continue launching, never `fatalError`, never block startup.

**D3 — the block logs its decision on every launch, one `NSLog`, and that log line is this task's only `ai`-verifiable evidence.**
`SMAppService.mainApp.status` is readable **only inside the calling bundle's own process**. This is a hard constraint on how the task can be tested, and it invalidates the obvious shortcut — see the probe trap in *Architectural notes*. A single log line that names the decision and the prior status is therefore not test scaffolding; it is the only way an agent with no UI can make a **persistent, system-wide state change** auditable at all. One line per launch, no loop, no polling.

**D4 (REVISED 2026-09-21 — measured) — the gate is decided per status case: register on `.notRegistered` *or* `.notFound`; never on anything else.**
`Project.md` §5 writes `status == .notRegistered`. **That condition is wrong on this machine and must not be restored.** Measured twice on macOS 26.6.2 with the installed bundle and no login item ever created for it: `SMAppService.mainApp.status` returns **`.notFound` (3)**, not `.notRegistered` (0). With §5's condition the code logged `no action, status=notFound(3)` and `register()` was never called — the task shipped a no-op. This is the same class of defect as task 04's §5 `install:` ordering: **§5 is a sketch; where measurement contradicts it, measurement wins.**

Per-case reasoning — write the code so each case states its own answer (a `switch` reads better than a `!=` chain here, and makes the new case visible in review):

| Status | Meaning | Decision |
|---|---|---|
| `.notRegistered(0)` | no BTM record for this bundle | **register** — nothing exists yet |
| `.notFound(3)` | BTM has no record / cannot find the service for this bundle | **register** — observed first-launch value on macOS 26; semantically also "nothing exists yet" |
| `.enabled(1)` | login item exists and is on | do nothing — already correct, and re-registering would re-fire the "added to Login Items" banner every launch |
| `.requiresApproval(2)` | the user switched it **off** in System Settings (or approval is pending) | **do nothing** — this is the whole point of the gate: we must never silently re-enable something the user turned off. Unchanged from the original D4 |
| any future/unknown case | unknown | do nothing — **fail closed**. A future SDK case must never fall into the register branch, so the `default:`/`@unknown default:` arm answers "do not register" |

Everything else stays: the `/Applications/` gate, `do/catch` (D2), the single `NSLog` (D3), and the rawValue-bearing `label(_:)` helper.

**D6 (NEW 2026-09-21 — measured) — `NSLog` output does not reach the unified log; the only way to read it is stderr capture.**
`log show --predicate 'process == "ActiveBrowser"'` returns **nothing** on this machine, for any window. The line only reaches the process's stderr, which is discarded when the app is launched by `open`/Launch Services. So every `ai` observation in this task runs the bundle's executable directly and captures stderr:
```sh
pkill -x ActiveBrowser; sleep 2
/Applications/ActiveBrowser.app/Contents/MacOS/ActiveBrowser > /tmp/ab06-run.log 2>&1 & AB=$!
sleep 4; kill $AB; sleep 1; cat /tmp/ab06-run.log
```
This **does** exercise the real bundle: `Bundle.main` is still `/Applications/ActiveBrowser.app`, the `/Applications/` gate passes (the measured line was `no action`, not `skipped`), and `SMAppService.mainApp` resolves to the installed app — so a `register()` from such a run creates the real login item for the installed copy. Two obligations follow: (a) never leave a directly-exec'd instance running — `kill` it, then **relaunch normally with `open -a ActiveBrowser`** so the machine ends with exactly one Launch-Services-launched agent; (b) do not add a second `NSLog`, a file log, or `os_log` to work around this — the stderr route is sufficient and D3's one-line budget stands.

**D5 — `Project.md` Phase 4 Verify step 7 splits across two tasks.** Step 7 reads *"Menu bar → Launch at Login on … Toggle off — expected: it disappears."* There is no menu bar until task 07 (same collision task 05 D1 recorded for Verify step 1). Resolution:
- The **on** half is covered here, by auto-registration rather than by a click, and confirmed by `user` step 6.
- The **off via System Settings** path is exercised here as the mandatory Reset (and is itself a real test of D4).
- The **off via the menu toggle** half is **deferred to task 07**, which must carry it as its own `user` step.

### Architectural notes and risks

- **The probe trap — do not fall into it.** `SMAppService.mainApp` resolves to *the calling process's own bundle*. A throwaway Swift/`swiftc` probe in `/tmp` that reads `SMAppService.mainApp.status` reports the **probe's** status, and calling `register()` there registers **the probe** as a login item — creating exactly the dangling-login-item-to-a-deleted-path problem this task exists to prevent, under a different name. There is no supported cross-process read of another app's `SMAppService` status. Hence D3's log line. (Task 02's reviewer legitimately used a throwaway probe bundle to prove delegate installation; that technique is **not** transferable here.)
- **`sfltool dumpbtm` is not available to us.** It requires root, and `~/Library/Application Support/com.apple.backgroundtaskmanagementagent/` is TCC-protected (a plain `ls` usually returns `Operation not permitted` without Full Disk Access). Test Step 7 tries it as *informational only* — both a listing and a permission error are acceptable outcomes, and neither can fail the task. **Never `sudo`** (guardrail: nothing in this project needs it, and a sudo-created artefact is not something the user can clean up from the GUI).
- **Ad-hoc signing is the most likely real failure.** BTM keys login items off the code-signing identity; an ad-hoc (`-`) signature has no stable Team/Developer ID. If `register()` throws, D2's log line will name the error, and that is a **finding to record, not a silent pass**: raise it as a `[RE-PLAN REQUEST]` only if the error indicates `SMAppService` is unusable for an ad-hoc bundle (that would be a genuine platform blocker affecting Phase 6's distribution story). A transient/permission error is a fix task instead.
- **macOS shows a notification banner** ("ActiveBrowser was added to Login Items") after a successful `register()`. It is a banner, not a modal — it does not block `ai` steps, but the user may see it appear while the batch runs. It is also a useful corroboration if the human happens to be watching.
- **HAND-OFF TO TASK 07 — read this before planning the toggle.** Task 07's `toggleLaunchAtLogin()` off-path calls `unregister()`, which sets the status back to `.notRegistered(0)` — and, on this macOS version, possibly straight to `.notFound(3)`. This task's gate re-registers on **both** of those, so **as written, an off-toggle would be silently undone at the next launch.** Task 06 in isolation is correct (its only off-switch is System Settings, which yields the sticky `.requiresApproval`), so this does not block this PR — but task 07 must resolve it, and the resolution belongs with the UI that creates the ambiguity: persist the user's choice (a `Settings` key, e.g. `launchAtLoginOptOut`) in task 07 and extend this gate with that one extra condition. Task 07 must treat `.notFound` **exactly like** `.notRegistered` in that logic — "no record exists" is not evidence that the user wants one, once an explicit opt-out is possible. `Project.md` §1 says "on first launch", which a persisted flag models honestly and a bare status check does not. **Do not pre-build that flag here** — it would be an orphan with no writer (guardrail §3).
- **Running the `build/` copy re-creates the duplicate Launch Services record that task 04 fixed.** `make install` now deletes `build/ActiveBrowser.app` by design, so Test Step 5 must `make bundle` to recreate it, and its cleanup is mandatory and ordered: `pkill` → `rm -rf build/ActiveBrowser.app` (delete first; the scanner re-registers a bundle that is still on disk ~1–3 s later, so `-u` alone loses that race — task 04 D2a) → `lsregister -u build/ActiveBrowser.app` → `lsregister -f /Applications/ActiveBrowser.app` → relaunch the installed copy. Use `-u`/`-f` only; **never `lsregister -kill` or `-r`**, which rebuild the whole database and would disturb every handler on the machine.
- **Test Step 5 must not run while the user is operating the default-browser dropdown** (task 05's `user` step). For the seconds that `build/ActiveBrowser.app` exists, two bundles claim `com.local.activebrowser` and `http`/`https`, and picking the wrong row binds the system default to a path this step then deletes. If the user is mid-dropdown, defer step 5 and record it as deferred.
- **Do not change the default browser and do not run `make clean` in this task.** The current default is **Arc** and task 05 may or may not have flipped it; either way this task neither needs nor touches it. `make clean` would delete `/Applications`… no — worse, it would delete `.build`/`build` while **leaving the login item in place**, which is exactly the state the Reset block exists to prevent.
- **Environmental linker warnings.** This machine has CommandLineTools but no Xcode, so each link emits one or two `ld: warning: search path '/Library/Developer/CommandLineTools/Developer/…' not found` lines. Every warning assertion here counts only warnings that are **not** those.
- **`log show` is a dead end here — measured (D6).** `log show --predicate 'process == "ActiveBrowser"' --last 3m` returns **nothing** for this app at any window width; the `NSLog` line reaches stderr only, and stderr is discarded when Launch Services starts the app via `open`. Do not spend time widening `--last`, adding `--info`/`--debug`, or switching the predicate to `subsystem`/`eventMessage`. Use the direct-exec stderr capture in D6, and always end such a step by killing the direct instance and relaunching with `open -a ActiveBrowser`.
- **A directly-exec'd run is a real run.** It registers the *installed* bundle (`SMAppService.mainApp` follows `Bundle.main`), fires the macOS "added to Login Items" banner, and creates persistent state — so it is subject to the same Reset block as any other launch. It is not a sandboxed probe (contrast the probe trap above, which is about a *different* bundle).
- **This task creates persistent state that survives reboot.** It is the first task in the run that does. The Reset block is mandatory and its *ordering* matters (see the note there about `−` vs the off switch) — `make clean`, quitting the app, and deleting `/Applications/ActiveBrowser.app` all leave the login item behind.
