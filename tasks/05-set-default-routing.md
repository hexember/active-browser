## Goal
Prove, on this machine, that ActiveBrowser routes real clicked links to the most recently focused browser — `Project.md` §3 Phase 4 Verify steps 2–6 and 8 — using the code already shipped by tasks 02 and 04. **This task adds zero production code**: it is a pure verification task whose deliverable is a recorded, reproducible test run plus the one `user` step that makes ActiveBrowser the system default browser.

## Spec (planner)

### Decisions to read before doing anything

**D1 — This task writes NO production Swift, and changes NO file except this task file.**
`Project.md` Phase 4 Verify step 1 is *"Menu bar → Set as Default Browser"*. That menu item lives in `UI/MenuBarManager.swift`, which is **task 07** (`Project.md` §3, task table). `MenuBarManager` does not exist yet, so the in-app action cannot exist yet either, and **Phase 4 Verify step 1 moves to task 07** — it is explicitly out of scope here. What remains of Phase 4 that is testable today is the routing behaviour itself (Verify steps 2–6, 8), and that behaviour was already implemented and reviewed:

| Behaviour under test | Already shipped by | File |
|---|---|---|
| focus → LRU stack update | task 02 | `Sources/ActiveBrowser/App/FocusObserver.swift` |
| LRU + running-first resolution | task 01/02 | `Sources/ActiveBrowser/Core/BrowserStack.swift` |
| candidate walk, self-filter, never-drop | task 02 | `Sources/ActiveBrowser/Core/URLDispatcher.swift` |
| cold-start bootstrap before the first URL | task 02 | `Sources/ActiveBrowser/App/AppDelegate.swift` |
| installed, Launch-Services-registered `.app` | task 04 | `Makefile` (`install:`), `Support/Info.plist` |

So there is nothing left to build for this phase — only to prove. The default is therefore set **by the user, in System Settings → Desktop & Dock → Default web browser** (the one `user` step), not by our code.

**D2 — Do NOT invent a trigger for `setDefaultApplication`.** No CLI flag, no `--set-default` argument parsing, no custom URL scheme (`activebrowser://set-default`), no `applicationDidFinishLaunching` auto-call, no hidden hot key. `Project.md` specifies exactly one call site for `NSWorkspace.setDefaultApplication(at:toOpenURLsWithScheme:)`: `MenuBarManager.setAsDefault()` (§5). Anything else is an orphan implementation (guardrail §3) and would have to be deleted by task 07. An auto-call would additionally be hostile: it fires macOS's confirmation dialog at login without the user asking.

**D3 — `open -a ActiveBrowser <url>` is the lever that makes this PR verifiable *today*, before the `user` step.**
`open -a ActiveBrowser https://example.com` hands the URL to the installed app through Launch Services' "open this URL *with this application*" path, which AppKit delivers to `AppDelegate.application(_:open:)` — the same entry point the default-browser role uses.

- **What it proves:** the real `URLDispatcher` candidate walk, the real `BrowserStack` LRU + running-first resolution, the real self-filter, the real fallback chain, the real cold-start bootstrap ordering, and that the installed bundle in `/Applications` actually receives and re-dispatches URL events.
- **What it does NOT prove:** that Launch Services' *handler lookup* for `http`/`https` resolves to `com.local.activebrowser` — i.e. that a link clicked anywhere on the system reaches us at all. That is exactly and only what the `user` step adds, and it is why steps 9–15 exist as well.

Both halves are required; neither substitutes for the other.

**D4 — Known semantic deviation: Verify step 5 opens the stack head, not `settings.defaultBrowser`.**
`Project.md` Phase 4 Verify step 5 says *"Quit every browser, `open …` — expected: the **fallback** browser launches"*. The shipped `BrowserStack.resolveTarget(fallback:)` is `running ?? items.first ?? fallback`, so when the stack is **non-empty** and nothing is running, the winner is `items.first` — the most recently focused browser — and `settings.defaultBrowser` is never reached. This is correct per `Project.md` §5's own skeleton and satisfies *never drop a URL*; only the prose in the Verify block is loose. Consequences for this task:

- Step 6 / step 13 expect **the most recently focused browser to relaunch**, not `settings.defaultBrowser`. Recording "opened in Brave, not the fallback" as a *failure* would be wrong.
- `settings.defaultBrowser` is genuinely exercised only with an **empty** stack. `BrowserStack` is in-memory and is not persisted, so restarting ActiveBrowser empties it — that is what steps 7 and 15 use.
- Correcting the Phase 4 Verify step 5 wording in `Project.md` is a later **docs-only** task, not this PR (same queue as task 04's §5 correction).

**D5 — Deterministic stack state is a precondition, not an assumption.** The stack is in-memory, un-inspectable until task 07's menu exists, and any focus event on any *included* browser mutates it. Every routing step therefore (a) starts from a known stack (preflight restarts the agent), (b) activates exactly one browser, (c) activates a neutral non-browser app (Finder) and asserts it is frontmost *before* the URL is issued, so the "which app became frontmost" assertion afterwards is non-vacuous. **Note `cmux` is in this machine's registry and claims `http`** (task 03's seeding recorded Safari / Brave / cmux / Arc): if the shell running these steps is hosted by cmux, activating it touches the stack. Never activate cmux between the browser activation and the `open`; if a routing step unexpectedly lands in cmux, that — not a dispatcher bug — is the first thing to check.

### Architectural notes and risks

- **Numbering vs. execution order (deliberate).** The `user` step is numbered **2** so the single blocking human action sits at the top of the table where the human will see it, but in wall-clock order the main session runs **1, then 3–8** (which are independent of it), and only then 9–15. The table states this; do not reorder the rows to match execution.
- **This is the one blocking `user` step of the whole run** (`CLAUDE.md`, batch mode). macOS shows a confirmation dialog when the default web browser changes; it cannot be scripted and must not be. Ask once, then keep building tasks 06–08.
- **`open -a` bypasses exactly one thing.** Handler *lookup*. It does not stub the dispatcher, does not fake the stack and does not change how `application(_:open:)` is invoked. Anyone reading steps 3–8 as a mock is misreading them; anyone reading them as a substitute for steps 9–15 is also misreading them (D3).
- **Task 02's known gap is on trial in steps 6, 7 and 13.** `NSWorkspace.open(_:withApplicationAt:configuration:)` is called with **no completion handler** (task 02, *Architectural notes*, "No open-failure retry"), so a browser that fails to *launch* from a quit state loses the URL silently. Those three steps are the first real exercise of launching a non-running browser. If one fails, that is precisely the `fix/` task task 02 pre-registered — not a re-plan of this task.
- **Quitting browsers closes the user's tabs.** Steps 5, 6, 12 and 13 require it; that is the minimum that can prove running-first resolution and the launch-from-quit path. Prefer `osascript -e 'tell application "Arc" to quit'` (a graceful quit — browsers restore their session on relaunch) over any `kill`. **Never `kill -9` a browser.** If macOS returns `-1743` / shows an Automation (TCC) prompt, record the step as blocked on that approval and ask the user; do not work around it with `kill -9`.
- **Prefer `lsappinfo` over `osascript` for reading state.** `lsappinfo front` + `lsappinfo info -only name <asn>` needs no TCC approval; `tell application "System Events" to … frontmost` does and can raise a dialog mid-run, which would silently turn an `ai` step into a `user` step.
- **Use a distinct path per step** (`https://example.com/s3`, `/s4`, …). It makes the landing tab identifiable in the browser afterwards, keeps the reset (close those tabs) unambiguous, and stops a browser from reusing an existing `example.com` tab and hiding a routing error.
- **`NSWorkspace.OpenConfiguration()` activates the target by default**, which is why "which app became frontmost" is a sound landing detector. Corroborate with `pgrep` for the launch-from-quit steps, where the stronger signal is that a previously-dead process now exists.
- **Do not run `make bundle` or `make run` during this task.** Either re-creates `build/ActiveBrowser.app`, and the Launch Services scanner re-registers it ~3 s later (task 04 D2a), putting a second ActiveBrowser row in the very dropdown the `user` step operates — where picking the wrong row binds the default browser to a path that a later `make clean` deletes. If the installed copy is somehow missing, the sanctioned repair is a single `make install` (which deletes the build copy again), followed by re-running the preflight.
- **Killing and relaunching ActiveBrowser does not disturb the handler binding.** `LSHandlers` names the bundle id; step 15 depends on that (macOS relaunches the registered handler on demand). `pkill -x ActiveBrowser` remains the only stop switch until task 07 ships Quit.
- **`Project.md` Phase 4 Verify step 7 (Launch at Login) is task 06** and must not be exercised here; no login item should exist at the end of this task (`Sources/` still has no `ServiceManagement` import).
- **Follow-ups this plan creates** (none in this PR): (1) the docs-only correction of Phase 4 Verify step 5's "fallback browser" wording per D4, bundled with task 04's pending §5 correction; (2) task 07 inherits Phase 4 Verify step 1 (the *Set as Default Browser* menu action) and must re-run it against the menu, including the confirmation dialog, as its own `user` step.
