## Goal
Turn the Phase 1 library into a real agent executable: add `App/AppDelegate.swift` (`@main`) with the single `NSWorkspace.didActivateApplication` observer (`App/FocusObserver.swift`) and the URL routing chain (`Core/URLDispatcher.swift`), so focus changes update the LRU stack and `application(_:open:)` always resolves some browser. Build-and-inspection only — there is still no `.app` bundle (that is task 03), so nothing can be clicked yet.

## Spec (planner)

### Decisions to read before writing code

**D1 — `Core/URLDispatcher.swift` is created as its own type (not inlined in `AppDelegate`).**
`Project.md` §4 lists the file and §1 lists `URLDispatcher` as a named component with its own responsibility; §5's skeleton inlines the body only because it is a sketch. Three reasons to honour §4 here: (a) the *never drop a URL* guardrail needs one auditable choke point, and this task deliberately makes that chain longer than §5's two lines (see D4); (b) task 07's *Routing to: <name>* menu line needs the same resolution logic and must not duplicate it; (c) `AppDelegate` stays short, so tasks 06 and 07 add lines instead of rewriting it. `AppDelegate.application(_:open:)` becomes a two-line forwarder. No §4 violation.

**D2 — `App/FocusObserver.swift` is created as its own type (not `appActivated(_:)` on `AppDelegate`).**
Same reasoning: §4 and §1 both name it. It owns the *one* observer registration and its lifetime rules in one place, which is exactly what Phase 2 Verify step 2 inspects. Deviation from §5's skeleton is intentional and behaviour-identical.

**D3 — `AppDelegate` is written so tasks 06 and 07 are pure additions.** This task writes **neither** `SMAppService` (task 06) **nor** `MenuBarManager` (task 07) — `MenuBarManager` does not exist yet, so the `menuBar` stored property is not declared either. `applicationDidFinishLaunching` is a short, ordered body (`bootstrapIfNeeded()` and nothing else in this task) with a one-line comment marking where each later task appends. Task 07 adds a `private var menuBar: MenuBarManager?` plus one construction line; task 06 adds its `/Applications`-gated `SMAppService` block as the last statement. Neither edits an existing line.

**D4 — the fallback chain is longer than §5's.** §5's `guard let appURL = NSWorkspace.shared.urlForApplication(withBundleIdentifier: target) else { return }` is a real dropped-URL hole: if the resolved bundle id is stale (browser deleted/renamed/on an unmounted volume) the URL is silently discarded, which violates guardrail §1. This task replaces the single-shot resolution with an ordered candidate walk (item 4 below).

**D5 — `NSWorkspace.shared.open(url)` (the plain, no-application form) is forbidden anywhere in this codebase.** We are (or will be) the registered `http`/`https` handler, so that call routes straight back into ActiveBrowser — an infinite loop. Every open must be `open(_:withApplicationAt:configuration:)`. State this in a comment in `URLDispatcher`.

### Architectural notes and risks
- **`@main` on an `NSApplicationDelegate`.** The entry point comes from AppKit's `NSApplicationDelegate.main()` protocol-extension default, which calls `NSApplicationMain`. If that fails to compile under Swift 6 / the CommandLineTools SDK, **the implementer is pre-approved** to write an explicit `static func main()` inside `AppDelegate.swift` (`let app = NSApplication.shared; let delegate = AppDelegate(); app.delegate = delegate; app.run()`) — same file, no new files, no `main.swift`. That substitution does **not** require a `[RE-PLAN REQUEST]`; anything else does.
- **Environmental linker warning (carried over from task 01).** This machine has CommandLineTools but no Xcode, so every link step emits exactly one `ld: warning: search path '/Library/Developer/CommandLineTools/Developer/Library/Frameworks' not found`. It is not produced by project code and is not fixable from the repo. Every warning assertion in this task is therefore written as "warnings that are not that one", and the raw `grep -c "warning:"` count is expected to be `1`, not `0`.
- **Cold-start ordering is the subtle bug in this phase.** AppKit may deliver the open-URLs Apple Event before `applicationDidFinishLaunching`. `bootstrapIfNeeded()` called from both entry points is the fix; reviewers should check that the `didBootstrap` flag makes it genuinely idempotent (the flag is set *before* the work, so a re-entrant call cannot double-register the observer).
- **No open-failure retry.** `NSWorkspace.open(_:withApplicationAt:configuration:)` is called without a completion handler, so a browser that fails to launch after the pre-flight `fileExists` check loses the URL. Adding a retry means a `@Sendable` completion handler and a `Task { @MainActor in … }` hop plus re-entrancy guards — disproportionate here, and the pre-flight check removes the common cause (stale path). **Deferred deliberately:** if Phase 4 Verify step 5 (all browsers quit → fallback launches) fails on a real machine, that becomes its own `fix/` task.
- **Self-filtering is inert until task 03.** Under a bare `swift build` binary `Bundle.main.bundleIdentifier` is `nil`, so the dispatcher's self-drop filters nothing. Write it so a `nil` self id simply matches nothing — no force-unwrap, no `precondition`. It goes live when the `.app` bundle exists.
- **`UserDefaults` domain differs between the bare binary and the bundled app**, so any seeding done by a non-bundled test run is invisible to the installed app later. Harmless now; do not run the built binary as part of this task's verification (there is no `Info.plist`, so it would appear as a foreground Dock app).
- **Newly installed browsers are not auto-included.** Seeding only fires when `includedBrowsers` is empty, so a browser installed after first launch will show up in the registry but unticked. That is Phase 5 / task 08 product surface — do not add auto-inclusion logic here.
- **`BrowserRegistry.refresh()` does not de-duplicate by bundle id** (noted by task 01's reviewer). After task 03, `make run` + `make install` can make Launch Services report two copies of one app. The dispatcher's candidate de-duplication (item 4, step 2) absorbs this for routing; the menu-side decision stays with tasks 07/08.
- **`resolvedTargetId()` is the seam for task 07.** Task 07 must call it rather than re-implementing resolution in `MenuBarManager`; flag it in the Implementation Notes so task 07 cannot miss it.
