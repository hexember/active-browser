## Goal
Insert the two remaining menu groups from `Project.md` §5 at the marker task 07 left in `MenuBarManager.rebuild()`: a *Browsers* submenu that ticks/unticks which installed handlers participate in routing — with the last ticked browser disabled so `includedBrowsers` can never become empty — and a *Fallback Browser* radio submenu over the included browsers that writes `settings.defaultBrowser`. This is the first task in which a menu click changes routing.

So **`Sources/ActiveBrowser/UI/MenuBarManager.swift` is the only file that may change.** No `Core/` change, no `App/` change, no `Makefile`/`Info.plist`/`Package.swift`/`Project.md`, no new `import` (still `AppKit` + `ServiceManagement`).
The one line deleted anywhere is task 07's marker comment at `UI/MenuBarManager.swift:99`, which this task consumes:
`// TASK 08 INSERTS THE *Browsers* AND *Fallback Browser* SUBMENUS HERE, FOLLOWED BY ANOTHER SEPARATOR.`
Task 07's own eight `rebuild()` elements, `refresh()`, `menuWillOpen(_:)`, `currentTargetName()`, `recentLine()`, `setAsDefault()`, `toggleLaunchAtLogin()` and `quit()` are **not** edited — new code is added around them, not through them.

**D2 — The bundle id travels on `representedObject`, not on `tag`.**
`NSMenuItem.tag` is an `Int`, so carrying a bundle id through it means storing an index into `registry.installed` and looking the id back up in the action. That lookup is only correct if the array the index refers to is the array that existed when the item was built — and `menuWillOpen` calls `registry.refresh()`, which can reorder and resize `installed` (a browser installed, renamed or uninstalled between two menu opens moves every index after it). An index is a reference into mutable state; the bundle id is the state. `representedObject` is `Any?` and holds the `String` directly, so the action is total:
```swift
guard let id = sender.representedObject as? String else { return }
```
Both new actions start with exactly that line, and neither reads `sender.title` (display names are not identifiers and are localised) or `sender.tag`.

**D3 — Every displayed state is derived, and `rebuild()` never writes.**
- Rows in *Browsers* = `installedUnique()` (D4), in that order — i.e. **all** installed handlers, ticked and unticked, exactly as §5's sketch shows `☑ Brave ☑ Chrome ☑ Safari ☐ Zoom`.
- Tick = `settings.includedBrowsers.contains(id)` → `.on` / `.off`.
- Rows in *Fallback Browser* = included browsers only (§5), radio = `id == settings.defaultBrowser`.
- Titles = `registry.entry(for:)?.name ?? id`, the same rule task 07's `recentLine()` uses.

`rebuild()` must not repair settings. Two consequences, both deliberate:
1. An id in `includedBrowsers` that is **not** currently installed (external volume, app temporarily moved) is simply not drawn; it is **not** pruned from `includedBrowsers`, so its tick returns when the app does. Silently deleting a user's choice because a disk was unmounted is the bug that "repair on read" always turns into.
2. A `defaultBrowser` that is not in the included set (only reachable by an external `defaults write`, since D6 keeps it consistent) shows **no** filled radio rather than being rewritten behind the user's back. Picking any row fixes it. This is also what makes `rebuild()` safe to call from `menuWillOpen` — a write there would make merely opening the menu mutate persisted state.

**D4 — De-duplicate the registry by bundle id before building either submenu.**
`BrowserRegistry.refresh()` does not de-duplicate: `NSWorkspace.urlsForApplications(toOpen:)` returns one entry **per copy on disk**, so two installs of the same browser (`/Applications/Brave Browser.app` and a stray copy in `~/Downloads`) yield two `Entry` values with the same `bundleId`. Left alone that draws the browser twice and — worse — makes the last-item guard count `2` for what is one logical browser, which is exactly the path that lets `includedBrowsers` reach empty. So:
```swift
/// Installed handlers, first occurrence per bundle id wins, registry (display-name) order preserved.
private func installedUnique() -> [BrowserRegistry.Entry]
```
built with an `order-preserving` filter over a `Set<String>` of seen ids, and used by **both** submenus **and** the guard count. Fixing this inside `BrowserRegistry` would be the better home, but that type also feeds `URLDispatcher.candidates()` and routing behaviour is out of this task's fence — recorded as a follow-up below, not done here.

**D5 — Submenus are separate `NSMenu` objects, so each needs its own `autoenablesItems = false`, and neither gets a delegate.**
Task 07 set `menu.autoenablesItems = false` on the **root** menu only (`:60`). `NSMenu.autoenablesItems` defaults to **`true`** on every newly created `NSMenu`, and it is a per-menu property. With it left on, AppKit recomputes each item's enabled state from the responder chain before display; since our items have `target = self` and `self` implements the action, AppKit would **re-enable** the very item the last-item guard disabled. So both `NSMenu()` instances created here set `autoenablesItems = false` immediately after construction. This is the single most likely way for this task to ship a guard that silently does nothing.
Neither submenu may set `delegate = self`. `menuWillOpen(_:)` is delivered to the *opening* menu's own delegate: if a submenu had this object as its delegate, hovering the submenu would run `registry.refresh()` + `rebuild()`, and `rebuild()` starts with `menu.removeAllItems()` — tearing down the menu tree AppKit is in the middle of displaying. The submenus are already fresh: the root's `menuWillOpen` rebuilds the whole tree before anything is drawn. Acceptance grep: exactly one `.delegate = self` in the file.

**D6 — The last-item guard, in two places, and why both.**
Define `includedInstalledIds()` = `installedUnique().map(\.bundleId).filter { settings.includedBrowsers.contains($0) }` — the ticks the user can actually see.
- **View:** when `includedInstalledIds().count == 1`, the item for that single id gets `isEnabled = false`. Every other row gets `isEnabled = true`. This is what `Project.md` Phase 5 Verify 6 asks for ("verify the menu does not allow an empty set") and it is authoritative only because of D5.
- **Writer:** `toggleBrowser(_:)`'s untick branch re-checks `guard includedInstalledIds().count > 1 else { return }` before removing. A disabled `NSMenuItem` is still reachable through accessibility and `NSMenu.performActionForItem(at:)`, and more importantly the invariant belongs to the code that writes the set, not to the code that draws it. If a future edit forgets D5, the set still cannot empty.

The invariant this protects is the **"Never drop a URL"** guardrail's first rung. With `includedBrowsers` empty, `FocusObserver` filters out every activation, the stack stays permanently empty, and every URL for the rest of the install's life is decided by `settings.defaultBrowser` alone — the app silently stops being the app. Guarding at the only UI that can empty the set is the cheapest possible place.

**D7 — Untick: write, prune, then migrate the fallback in a deterministic order.**
Order inside the untick branch, exactly:
1. `included.remove(id)`, then `settings.includedBrowsers = included` (persist first, so every later read is off the stored truth).
2. `stack.prune(keeping: settings.includedBrowsers)` — the unticked browser stops being a routing candidate immediately, which is what makes Phase 5 Verify 2 observable.
3. `if settings.defaultBrowser == id { settings.defaultBrowser = orderedIncluded().first ?? settings.defaultBrowser }` (Verify 5).

"**First**" must be pinned down, because `includedBrowsers` is a `Set<String>`: Swift seeds `Set` hashing per process, so `included.first` and `for id in included` give a **different order on every launch** — the same untick would move the fallback to a different browser each time, and no bug report about it would ever reproduce. The only ordering available is `registry.installed`'s, which `refresh()` sorts by display name, case-insensitively ascending. So:
```swift
/// Included browsers in menu order: installed ones in registry display-name order first,
/// then any included-but-not-installed ids in bundle-id order. Deterministic by construction;
/// `Set` iteration order is not, and must never be used to choose a fallback.
private func orderedIncluded() -> [String]
```
`?? settings.defaultBrowser` is there so the key is **never written `nil`**: under the D6 guard the list cannot be empty on this path, but a `nil` fallback would weaken the never-drop chain for no benefit. `chooseFallback` and this migration are the only two writers of `defaultBrowser` in the file — two assignments total.

**D8 — Re-tick touches settings and nothing else.**
The tick branch is `included.insert(id)` + one write. It must **not** call `stack.touch(id)` and must **not** change `defaultBrowser`. `stack.touch` means "the user focused this browser", and it did not happen: fabricating it would move the routing target — and the *Routing to:* line — onto a browser the user merely re-enabled, from a click that only said "allow this one again". `Project.md` Phase 5 Verify 3 says the expected behaviour out loud: *"it participates in routing again **on next focus**"*. The stack refills from the real `NSWorkspace` notification. Acceptance grep: no `stack.touch` anywhere under `UI/`.

**D9 — The fallback submenu is a radio group by mutual exclusion, not by glyph.**
Each row: `state = (id == settings.defaultBrowser) ? .on : .off`. Do **not** put `●`/`○` in the title and do **not** install custom `onStateImage`/`offStateImage`: AppKit's checkmark is the platform convention for a mutually-exclusive menu group (Finder's *View ▸ Sort By*, Safari's encoding menus), and `Project.md` §5's `● / ○` is sketch notation for "radio", not a glyph requirement. Mutual exclusion comes from `rebuild()` recomputing every row against one stored id, which is structurally incapable of showing two filled rows.
The currently selected row stays **enabled**. Disabling it would make the group look broken (a radio whose selected option is greyed reads as "unavailable"), and re-picking it is a harmless idempotent write.

**D10 — Rebuild discipline, and the self-filter guard on the two writers.**
Both actions end with `rebuild()` **then** `refresh()` — never with in-place mutation of `sender.state`. `rebuild()` recomputes ticks, radio and the enabled-guard from the persisted truth; `refresh()` is needed because both actions can change the routing target *immediately* (an untick prunes the stack head; a fallback change retargets an empty stack), and the status item's tooltip would otherwise stay stale until the next focus event. Calling `menu.removeAllItems()` from inside an action is safe: AppKit dismisses the menu before it sends the item's action, which is the same thing task 07's `toggleLaunchAtLogin()` already does (`:207`).
Both writers reject this app's own bundle id before writing — `id.caseInsensitiveCompare(Bundle.main.bundleIdentifier ?? "") != .orderedSame`, mirroring `URLDispatcher.candidates()` (`Core/URLDispatcher.swift:82-87`). It is unreachable, because the rows are built from `registry.installed`, which already drops self — but `includedBrowsers` and `defaultBrowser` are named explicitly in guardrail §1 and this file is now the only place in the codebase where user input writes either. One helper, used by both actions.

**D11 — Persistence across relaunch (Phase 5 Verify 7) is already free and gets no code.**
Both keys are `UserDefaults`-backed (`Core/Settings.swift`), every write goes through those setters, and `AppDelegate.bootstrapIfNeeded()` re-seeds **only** when `includedBrowsers.isEmpty` (`App/AppDelegate.swift:92-97`) — which D6 makes unreachable. So a relaunch restores exactly what the menu wrote. Verify 7 is therefore a **test step**, not a checklist item; adding any "save on quit" code here would be a second writer for state that already has one.

### Architectural notes and risks

- **The `autoenablesItems` default is the trap in this task.** It is `true` on a fresh `NSMenu`, it is per-menu, and when it is on AppKit's validation pass runs *after* our `isEnabled` assignment and overrides it. A guard that is implemented correctly and then silently disabled by a default value is indistinguishable, in a screenshot, from a guard that works — which is why D6 also puts the check in the writer and why the `user` step for it is phrased as "try to untick it and confirm nothing happens", not "confirm it looks grey".
- **`Set` ordering is a real non-determinism, not a style point.** Swift's `Set` uses a per-process hash seed, so `includedBrowsers.first` genuinely differs between launches. Any fallback migration built on it would produce a bug that never reproduces twice. D7's `orderedIncluded()` is the only ordering source this file may use.
- **Registry duplicates (D4).** Unfixed in `BrowserRegistry`, this would also let `URLDispatcher.candidates()` list a browser twice — harmless there, because `candidates()` de-duplicates, which is precisely why the registry has survived without it. The menu is the first consumer that cannot tolerate it. **Pre-registered follow-up (not this PR):** move the de-duplication into `BrowserRegistry.refresh()` and delete `installedUnique()`; it touches routing input, so it needs its own task and its own routing re-test.
- **`menuWillOpen` rescan now has a visible consequence.** Task 07 could only prove the rebuild ran by watching *Routing to:* change; from this task, a newly installed browser appears as a new row in *Browsers*. Proving that still requires actually installing a browser, which is out of proportion — and planting a fake `.app` that claims `https` would pollute the user's Launch Services database and default-browser dropdown, so it is forbidden here as it was in task 07. The check is inherited forward, unproven, and said so.
- **Unticking the browser you are currently routing to changes routing mid-session, by design.** `stack.prune` drops it, so the very next link goes elsewhere. The tooltip is refreshed in the same action (D10) so the status item cannot claim a target that has just been excluded.
- **The fallback submenu will list `com.cmuxterm.app`.** It is a legitimately registered `https` handler on this machine and is in `includedBrowsers`; it is not a browser in any useful sense, but filtering "real browsers" would mean a hardcoded allow-list, which is worse. Untick it in the *Browsers* submenu if it is unwanted — that is exactly what the submenu is for. The `user` steps name it so it is not filed as a bug.
- **`defaults write` on `com.local.activebrowser` while the app runs is a footgun** (cfprefsd caching plus the running process writing the same keys). Every `ai` step below kills the app, writes, then launches — and every step that writes restores the exact four-id array and `company.thebrowser.Browser` before the run ends. The user's own testing and tasks 09–10 depend on that state.
- **This task does not change the default-browser binding and must not.** `setAsDefault()` is task 07's and is untouched; the user's system default stays Arc through the whole `ai` run. `ai` routing checks use `open -a ActiveBrowser <url>`, which reaches the identical `application(_:open:)` entry point (task 05 D3).
- **Phase 5 Verify coverage:** steps 2–7 land here in full. Step 1 and step 8 were task 07's and are not re-run. Phase 5's *Reset* is Phase 4's reset, which tasks 05/07 already own; this task adds one reset of its own — the `com.local.activebrowser` include/fallback state.
